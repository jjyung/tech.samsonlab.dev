AI 軟體工廠從需求分析到交付，怎麼安排人工審查與驗收？拆解 Stripe、OpenAI 和 StrongDM 的做法

一張需求進來，我們通常先問清楚要解決什麼問題，寫下驗收條件，再做設計、改程式、跑測試，最後開 PR。即使用 AI 幫忙寫某段程式，下一步該做什麼，通常還是由工程師決定和推進。

如果從需求進來的那一刻，就讓 AI 接手推進呢？讓它先找出沒講清楚的地方、提出規格和計畫，等人確認後做設計、實作、跑測試，再把證據和 PR 一起交給審查者。流程也可以接到部署後，讓 AI 觀察結果。工程師仍負責關鍵決策和放行。

我在〈從測試金字塔到信任系統〉問過：AI 說做完了，我們要看什麼證據才敢上線？後來整理 Lauren Tan 的演講時，我把問題往前移：哪些錯能靠程式碼庫的設計和可執行的檢查先擋下來，不用等人審 PR 才發現？

到了軟體工廠，這兩個問題都得在每張工單上回答。下一張工單進來，能不能跑到該跑的檢查、留下足夠的驗收證據，沒把握時停下來交回給人？

品質的地基要在擴大自動化之前打好。程式碼庫要有值得沿用的做法，測試要能抓到錯誤，審查者也要拿得到證據。這些工作如果還仰賴人每次從頭補救，多開幾個 Agent 只會讓待審的 PR 堆得更快。

一張工單怎麼跑完軟體工廠的流程

「Software factory」並不是 AI 時代才出現的詞。軟體工程長期以來都在借用製造業的比喻，思考如何讓交付更有系統。如今這個詞被重新拿來描述 Agent 參與下的開發流程，但目前仍沒有單一、固定的業界定義。[1]

以人保留放行權的流程為例：

flowchart TD
    A["需求、問題或告警"] --> B["AI 釐清需求，提出規格、驗收條件與計畫"]
    B --> C{"人確認方向與驗收條件"}
    C -->|需要調整| B
    C -->|確認| D["AI 設計、實作與測試"]
    D --> E["AI 提交 PR 與驗收證據"]
    E --> F{"人審查並決定是否放行"}
    F -->|退回修正| D
    F -->|放行| G["部署"]
    G --> H["AI 觀察部署結果"]
    H -->|未達預期，交回人工判斷| I["人決定再調查、叫停或回滾"]

每個步驟都要有觸發條件。Agent 接手時要知道前面做了哪些決定、現在該跑什麼檢查，以及遇到問題要交給誰。有人只自動化其中一段，也有人試著把流程延伸到正式環境。是否自動合併或部署，並不是所有軟體工廠共同的定義。

一個 coding agent 可以是工廠裡的執行者。harness 是它執行任務時使用的工具、上下文、權限和回饋環境。軟體工廠則把這些執行能力接到工作流程、團隊決策和產品營運上。這是本文為了便於比較採用的區分，不是各家一致使用的術語。

AI-DLC 怎麼分配人與 Agent 的工作

AI 輔助的 SDLC，還是由工程師推進工作，需要時請 AI 補程式碼、寫測試或整理文件。AWS 在 2025 年提出的 AI-Driven Development Lifecycle（AI-DLC）則改了分工：讓 AI 先提計畫、主動問清楚不確定的地方，再執行核准後的工作。人提供目標和限制，驗收結果，也保留關鍵決策權。[2]

我在演講裡用過一個比喻：工程師正在從工人變成工頭。以前多半是自己動手做。現在把一部分工作交給 Agent，就得先交代清楚要做什麼、哪些地方不能動、怎樣才算做完。結果不對，還得有人判斷是要重做、叫停，還是回滾。即使程式碼交給 Agent 寫，工程師還是得對交付結果負責。

這是人與 AI 的分工，還不等於有一座軟體工廠。團隊可以照 AI-DLC 一起釐清需求、做設計，卻不把任務交給背景 Agent。也可以只把套件升級做成持續運作的流程，而不採用 AI-DLC。AWS 的原始提案把人與 AI 的分工放在三個階段：

階段AI 參與的工作人的責任
Inception將業務意圖整理成需求、工作項目與計畫，提出待釐清的問題確認需求、優先順序和業務取捨
Construction根據已確認的上下文提出設計、程式碼與測試參與技術決策，檢查方案是否符合目標
Operations運用前面累積的上下文協助基礎設施與部署監督操作並對重要決策負責

三個案例，三種驗收方式

Stripe 讓 Agent 開 PR，由人審查。OpenAI 把流程延伸到部署後，確認效能有沒有恢復。StrongDM 則拿掉人工程式碼審查，改用情境測試取得驗收證據。

Stripe：Agent 完成任務，人仍審查程式碼

Stripe 的 Minions 從頭到尾完成程式修改並提出 PR，但由人審查程式碼。Stripe 表示，這套系統每週產出超過一千個上線的 PR。[3]

每週的 PR 數量是 Stripe 自行公布的產出指標。要評估品質與效益，還得看這些改動上線後的缺陷、重做與成本。

OpenAI：從效能告警走到修復後驗證

OpenAI 的 Performance Factory 聚焦在效能退化。告警觸發調查，Agent 提出修正，再由工程師審查並部署。部署後，Agent 繼續檢查效能是否恢復。任務狀態和調查結果存在單次執行之外，流程可以停下來等人或等部署，再從上次進度接著跑。[4]

這張工單不會在 PR 合併時結案。如果部署後指標毫無改善，就回到調查階段。工廠不必包下整個開發生命週期，但要知道自己負責的工作何時才算完成。[4]

OpenAI 同時提到，Agent 有時會停在第一個看似合理、卻解釋不了所有現象的原因，因此另開一個 Agent 工作階段來核對診斷。在人工檢視的 100 個根因建議中，70% 被評為正確，其餘需要進一步釐清或不足以建立因果關係。另一個 Agent 可以幫忙找診斷的漏洞，團隊仍得核對支持根因的證據。[4]

StrongDM：拿掉程式碼審查，驗收證據從哪裡來？

StrongDM AI 團隊在 2026 年分享了較激進的實驗：由規格與情境驅動 Agent 編寫程式，團隊設定不由人手寫或審查程式碼的規則。這類高度自動化模式常被稱為 dark factory。[5]

如果 Agent 能修改測試，測試全綠也可能只是驗收標準被放寬了。StrongDM 用描述端到端行為的 scenario 驗收，部分情境放在程式碼庫之外，並模擬外部服務來重跑情境。代價是這些情境和模擬環境都得維護。模擬跑通，也不代表真實服務會有完全相同的行為。

把測試和驗收證據接進每張工單

Lauren Tan 的團隊先整理程式碼庫、把反覆犯的錯寫成可執行的檢查，也讓 Agent 能實際操作應用程式、留下可供審查的結果。先有這些，後來才談得上在發布後自動測試、提出修正 PR，甚至自動合併部分修正。演講沒有交代合併門檻，不能只照搬最後一步。[6]

到了工廠這一層，還要讓每張工單都走得到這些檢查。鄭淳尹在《網管人》分享的做法，把開單、派工、隔離執行和交付分開。開單時先補齊重現方式和驗收條件。執行放在受限環境。交付時用堆疊式 PR（stacked PRs）拆開測試、實作與文件，讓審查者能先看測試抓住了什麼，再看程式怎麼修。[7]

拆成三張 PR 只是其中一種做法。小改動用一張 PR 也可以，只要審查者看得出同一個測試在修正前為什麼失敗、修正後為什麼通過。對高風險變更，再保留由團隊維護的獨立驗收情境，避免負責修正的 Agent 同時改寫放行標準。型別與 lint 能擋掉已知錯誤，行為測試才回答這次的需求有沒有做到。兩者都不能替團隊決定什麼風險可以接受。

先讓 Agent 重現問題，再讓它提修正

不用先蓋一整座平台。以「登入偶爾逾時」為例，可以先用現有的工單和 CI，在隔離環境裡試跑一段小流程：

  1. 把工單寫到能重跑： 填上受影響版本、重現步驟和預期行為。資訊不夠就交回給人，不讓 Agent 自己猜驗收標準。
  2. 先收證據，不改程式： 用測試資料重跑，留下版本、結果和相關紀錄。分清楚「重現了逾時」和「這次沒重現」，不要把後者當成問題已解決。試點不給正式環境寫入權限。
  3. 量核對時間，再決定要不要擴權： 記重現結果對不對、人花多久核對、重跑了幾次。等流程穩定，再挑重複、低風險的案例讓 Agent 提修正 PR。以登入逾時來說，審查者除了看逾時能否重現、修正後是否消失，也要確認原有的登入驗證仍然有效。

到了要部署登入修正的階段，先由人決定是否放行，並約好上線後看什麼：例如逾時率有沒有回到基準、登入失敗率有沒有上升。指標沒改善就把工單交回調查。如果登入失敗率反而升高，值班工程師要能叫停流程、回滾部署。

評估試點時，除了交付時間，也要算重做、缺陷和執行成本。換模型或改流程時，Warp 創辦人 Zach Lloyd 建議保留可查的設定、執行紀錄和評估結果，讓團隊能用自己的代表性任務比較。[8] 2025 年 DORA 報告也觀察到，AI 採用與交付吞吐量、產品表現呈正向關聯，同時與交付穩定性的負面結果相關。這些關聯不能證明因果，但提醒團隊別只看速度。[9]

即使 AI 能從一張需求一路做到 PR，CI 全綠也只代表它通過了目前的檢查。要不要讓 Agent 再接手一步，先用下一張工單回答：還缺什麼證據、誰有權放行，以及看錯了要怎麼停、怎麼退回來。

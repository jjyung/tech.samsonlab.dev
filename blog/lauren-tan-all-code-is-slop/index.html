Coding Agent 寫的都是 Slop？Lauren Tan 談如何用程式碼設計與可執行檢查擋下常見錯誤

如果 Coding Agent 一再犯同樣的錯，先看看能不能用 API 設計、型別或 lint 規則擋下來。比起在 AGENTS.md 再補一條提醒，這些做法不必仰賴 agent 每次都讀懂並遵守文字。

SpaceXSI 主任工程師 Lauren Tan（@poteto）在 AI Engineer Code Summit 2026 的演講〈All Code Is Slop (Except Mine)〉中，用團隊的開發經驗說明：改善 agent 工作的環境，可以讓錯誤更難發生，也讓結果更容易驗證。[1]

Tan 曾在另一篇貼文中提到，品質不佳的程式碼並不是 AI 才帶來的問題：人類寫的程式碼也有同樣的狀況。多數軟體團隊本來就在速度、成本與品質之間取捨，再透過測試和可觀測性來降低風險。[2]

信任不是靠提示詞堆出來的

Tan 用一個「信任金字塔」說明，團隊可以從幾個層次改善 agent 的工作環境（01:03:09）：[3]

  1. 程式碼庫設計： 透過 API、架構與重構，減少錯誤的選擇。
  2. 可執行的檢查： 使用 lint、型別系統、編譯器與測試，擋下已知問題。
  3. 行為驗證： 執行程式、檢查結果，必要時搭配形式化驗證。
  4. 文字指引： 用規則、skills 和 AGENTS.md 補充需要判斷的情境。
  5. 人工審查： 檢視自動化機制無法充分涵蓋的風險與證據。

把能自動檢查的限制交給工具，文字指引和人工審查就能留給真正需要判斷的問題。

Tan 把程式碼庫比喻成花園。Agent 會參考既有程式碼，過時寫法和暫時修補也可能變成下一次修改的範本。清掉這些寫法，就少了讓 agent 照抄的機會。

用框架和 lint 擋下重複出現的錯誤

Tan 分享了團隊為 Grok Bot 開發的 Electron 客戶端框架 Dune。團隊把開發桌面應用程式的經驗放進框架和檢查機制，減少每次 review 都得重新討論的問題（01:06:17）。[3]

例如，團隊限制 React 的 useEffect 只能出現在特定框架內部，而不是要求 agent 在所有產品程式碼裡都正確處理它的細節。這是該團隊針對自身架構做出的選擇，不代表所有 React 專案都應該禁用 useEffect。

另一個例子是 Electron 的程序邊界。團隊以目錄區分 main process 與 renderer，再透過依賴分析和 lint 規則限制不適當的跨邊界匯入。目錄結構告訴開發者和 agent 程式碼應該放在哪裡；檢查機制則負責執行這個約束。

Tan 也提到，agent 有時會用註解解釋為什麼需要暫時修補。下一個 agent 讀到說明，可能把修補當成慣例照抄。團隊因此嚴格限制產品程式碼的註解，部分改用會指出修正方向的 lint 錯誤訊息（01:08:23）。[3] 不必照搬他們的註解政策；遇到一再出現的修補，可以先問能不能用 lint 或 API 設計堵住源頭。

從檢查 diff，擴大到檢查行為與證據

即使架構和靜態檢查能排除部分錯誤，團隊仍需要確認程式實際做了什麼。Tan 分享的做法是讓 agent 能夠執行應用程式、使用除錯工具，並產出影片、截圖、圖表或驗證結果，供人審查（01:11:00）。[3]

她的團隊還建立了從使用者角度描述應用功能的 feature map，讓人與 agent 能用共同詞彙指認介面；可重複使用的 CLI 和操作工具，則讓驗證步驟更一致。

對特定問題，團隊也用 TLA+ 對跨裝置通知流程做模型檢查、用 Lean 證明部分演算法的性質，並以性質導向測試檢查 UI（01:12:21）。[3]

兩種工具回答的問題不同：TLA+ 用來描述系統如何改變狀態，可搭配 TLC 檢查模型是否有違反規格的行為；Lean 是證明助理，用來檢查某個性質能否從給定的定義與假設推導出來。兩者都不會自動保證正式環境的實作和模型一致。[4] [5]

審查時除了看 diff，也可以看修改能不能跑、使用者流程是否符合預期，以及測到了哪些關鍵狀態。想找可搭配這些驗證步驟的工具，可以參考站內的 AI Coding Agent 工具箱。

先把內部流程做好，再放大自動化

Tan 表示，團隊在演講前一個月將約 11,000 個 pull request 交付到正式環境，撤回率約為 0.5%，部分客戶端效能指標也有改善（01:15:02）。[3] 她另外分享，自己花了約六個月改善 agent 的工作環境，才走到能交付數千個 PR 的階段（01:03:09）。[3]

這些是演講者分享的團隊成果，不是對照實驗。PR 數量不等於使用者價值，revert 比率也無法涵蓋所有缺陷；不同產品的風險、團隊規模與 PR 切分方式不同，不能直接拿數字當成其他團隊的目標。

她在演講結尾描述了更高程度的自動化：新版本發布後，系統會啟動 agent 操作並測試應用程式，對發現的問題建立修正 PR。這套流程可自動合併修正 PR，但演講沒有說明合併門檻（01:17:45）。[3] 這個做法建立在團隊先前投入的架構、檢查與驗證之上，不是建議所有專案立即開啟自動合併。

可以先挑一個 agent 常犯的錯：清掉會被照抄的舊範例，能用 API 設計擋住就改 API，否則加一道檢查，再補上能重跑的行為驗證。等這套做法能穩定擋錯、驗證結果，再考慮增加 agent 數量或擴大自動化。

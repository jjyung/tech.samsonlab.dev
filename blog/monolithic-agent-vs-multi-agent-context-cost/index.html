Monolithic Agent 與 Multi-Agent，先看 Context Isolation，再看 Context Cost

重點摘要

拆 multi-agent 的一階動機，是做：

context isolation

也就是避免不同任務、角色、工具與狀態彼此污染。

context pollution 常見會長這樣：

  • 不相關的 domain knowledge 被一起塞進 prompt
  • 上一階段的中間狀態殘留到下一階段
  • 不同角色的 instructions / guardrails 互相干擾
  • 長 session 裡的工具痕跡把局部任務越攪越混

成本通常是二階問題。

拆開之後，每個 agent 的 local context 可能更乾淨； 但 system-level cost 可能變高，也可能變低，取決於：

  • 幾次 model calls
  • 幾次 routing / delegation
  • 幾次 handoff summary
  • 幾份重複的 instructions / tools schema
  • 幾次重複 retrieval
  • 最後還要不要再做一次 synthesis

所以更準確的說法不是：

multi-agent 比 monolithic agent 更便宜。

而是：

multi-agent 常常是在用更多 coordination cost，換更乾淨的 local context 與更強的隔離邊界。

反過來說，monolithic agent 常常是在用更大的 shared context，換更強的 continuity 與更少的 handoff， 但也更容易累積 context pollution。

但這裡還有一個常被忽略的前提：

不是所有 multi-agent 都有一樣的成本模型。

有些子 agent 會從 fresh context 開始，有些則會繼承父 agent 的上下文、狀態，甚至 prompt cache。

這個 execution mode 的差別，會直接改變你到底是不是在重複付 shared context 的成本。

這代表 agent topology 本身，不只是模組化問題。

它同時也是：

  • context architecture
  • cost architecture

的一部分。

先校正問題

monolithic agent 與 multi-agent 這個選擇，至少牽涉這幾個維度：

  • modularity
  • specialization
  • maintainability
  • team ownership
  • cost

這些都很重要。

但這裡其實有兩個問題，而且順序不能反：

  1. 這個任務到底更需要 context sharing，還是 context isolation？
  2. 在選定 topology 之後，它的 context cost shape 會長什麼樣子？

這篇主要談第二題。

但如果第一題沒先答對，後面的成本比較很容易失真。

因為 topology 一變，不只是成本的組成方式會跟著變， 連 reasoning quality、state cleanliness 與 tool interference 都會一起變。

如果你只看單次 call，很容易得出錯誤結論。

更實際的算式通常比較像：

Per-task cost
≈ sum(每一次 model call 的 local context)
+ routing / handoff overhead
+ repeated prefix cost
+ final synthesis cost

所以真正該問的不是：

哪一種 agent 比較進階？

也不是：

哪一種 agent 天然比較省？

而是先問：

這個任務先需要 context isolation，還是 context sharing？

然後再問：

哪一種 topology，對我的任務分布、context sharing pattern 與 workflow，總成本更低？

先講結論

如果把這件事濃縮成三句話，大概會是：

Multi-agent 一階上在解的是 context pollution，不是 token 價格。 Monolithic 一階上在保留的是 shared context continuity，不是架構上的簡單。 成本是這兩種選擇各自帶出的二階效果。

所以它們不是「誰比較高級」的關係， 也不是「誰天然比較省」的關係。

它們是兩種不同的上下文管理方式， 也會對應到兩種不同的成本形狀。

Monolithic Agent 的共享優勢，與它帶來的成本形狀

Monolithic agent 不一定代表系統很原始。

它也可能只是表示：

  • 一個主要 agent 負責規劃
  • 一個主要 agent 負責工具使用
  • 一個主要 agent 保持大部分 session continuity

它的優勢不只在成本，也在於 shared context continuity。

1. 共享上下文天然完整

如果整個任務高度依賴同一份背景資訊，例如：

  • 同一個 repo context
  • 同一組 coding rules
  • 同一份 architecture summary
  • 同一段 session history

那 monolithic agent 天然比較容易共享這些資訊。

你不需要一直做：

  • handoff summary
  • state projection
  • agent 間上下文轉譯

2. 比較容易重用 stable prefix

如果 system prompt、tools schema、repo policies 都相對穩定， 那 monolithic agent 通常比較容易維持一個穩定前綴。

這代表：

  • caching 比較容易命中
  • prefix reuse 比較直接
  • 不需要每個 specialist 都重送自己的規則

3. model call 數量通常比較少

如果沒有拆 agent，你通常也就少了：

  • coordinator call
  • transfer call
  • specialist invocation call
  • synthesis call

這一點很直接。

但 monolithic agent 的缺點也同樣明顯。

4. 它很容易把不相關的東西一起背著跑

一旦一個 agent 同時要處理：

  • 多種 domain knowledge
  • 很多 tools
  • 很長的 session history
  • 很多 guardrails

那 prompt 很快就會變成一個大雜燴。

典型的浪費是：

使用者只需要其中 10% 的知識， 但 agent 每一輪都背著 100% 的 context 在跑。

而且這裡的問題不只是在成本。

當同一個 prompt 裡塞進太多不相關資訊、過時狀態，甚至彼此矛盾的指令時， 模型也更容易出現注意力分散、約束抓錯與回應漂移。

把這些現象統稱成 hallucination，常常會太粗。 在 agent 系統裡，它更接近 context competition 與 state inconsistency 的結果。

5. 成本壓力會往 compaction 移動

Monolithic agent 的典型成本問題，不一定是 routing。

而是：

  • session history 不斷膨脹
  • compaction 壓力上升
  • tool traces 越來越長
  • retrieval snippets 越加越多

換句話說，monolithic agent 往往更依賴：

cache discipline + compaction discipline

Multi-Agent 的核心價值，與它帶來的成本形狀

Multi-agent 的優勢通常很吸引人。

但更準確地說，它的核心價值不是「把 prompt 變便宜」， 而是把一個大問題拆成多個上下文邊界比較乾淨的局部問題。

你可以讓每個 agent 只處理：

  • 自己的 instructions
  • 自己的 tools
  • 自己的知識域
  • 自己需要的少量上下文

這個方向之所以成立，是因為它在解一個 monolithic agent 很難解的問題：

context isolation

換句話說，multi-agent 先在處理的是：

  • 避免不相干的知識一起進 prompt
  • 避免不同角色的目標互相覆蓋
  • 避免中間狀態在長流程裡持續污染後續判斷
  • 避免 tools / memory / guardrails 全部堆在同一個決策面上

這也是為什麼 ADK 的官方文件會把 multi-agent 系統描述成一組可組合的 hierarchy、workflow agents 與 interaction mechanisms，而 LangChain 的 multi-agent 文件也直接把 context management 視為核心動機之一。

成本則是這個設計決定之後，才要看的 downstream effect。

但 multi-agent 不是免費午餐。

更準確地說，multi-agent 的成本不只取決於你有沒有拆 agent， 也取決於子 agent 是怎麼被啟動的。

如果每個 worker 都從 fresh context 開始，handoff、prefix 與 retrieval duplication 會更明顯。 如果 execution mode 允許它繼承父 agent 的上下文或共享快取，那成本形狀又會不一樣。

1. 每個 specialist 變小，不代表整個系統變便宜

如果系統拓樸變成：

  • coordinator
  • specialist A
  • specialist B
  • final synthesizer

那你的成本就不再是單一 prompt。

而是很多局部 prompt 的總和。

每個局部 prompt 都可能包含：

  • agent-specific instructions
  • tool definitions
  • handoff summary
  • retrieval 結果
  • local history

2. handoff 會變成新的 token sink

agent 拆開之後，最常被低估的成本就是：

handoff summary

因為子 agent 不是憑空知道前面發生了什麼。

你通常需要把這些資訊重新包裝後送進去：

  • 任務目標
  • 已知限制
  • 目前狀態
  • 前一步產出
  • 需要避免的錯誤

如果 handoff 做得不好，multi-agent 很快就會變成：

同一批事實被不同 agent 用不同 wording 重複講很多次。

這通常發生在 fresh spawn 的 worker 模式。

如果子 agent 可以直接繼承父 agent 的上下文，handoff 就不一定要濃縮成一大段 summary， 而可能只需要一個很短的任務指令。

3. duplicated prefix 可能比你想像中多

如果沒有共享機制，每個 specialist 往往都會有自己的：

  • role prompt
  • guardrails
  • tool schema
  • memory instructions

單看每個 agent 都不大。

但把所有 calls 加總後，你可能只是把一個大前綴，拆成很多個中型前綴反覆重送。

這是很典型的 failure mode，但不是 multi-agent 的必然屬性。

如果 runtime 支援 inherited context、shared state，或直接重用 parent prompt cache， 那 duplicated prefix 的問題可以明顯下降。

4. routing 錯了，成本不只浪費一次

multi-agent 還有一個 monolithic agent 沒那麼強的成本風險：

misrouting

如果 coordinator 先叫錯 specialist，再轉給另一個 specialist， 你付的不只是一次錯誤判斷。

你付的是：

  • 一次 coordinator call
  • 一次錯誤 specialist call
  • 一次新的 handoff
  • 一次真正需要的 specialist call

所以 multi-agent 更依賴：

routing discipline + handoff discipline

兩種成本流向看起來其實不一樣

把它們畫成圖，會更直觀。

flowchart LR
    subgraph Mono[Monolithic Agent]
        U1[User Task] --> A1[Single Agent]
        A1 --> C1[Shared Context]
        A1 --> T1[Tools / Memory]
    end

    subgraph Multi[Multi-Agent]
        U2[User Task] --> R[Coordinator]
        R --> H1[Routing / Handoff Context]
        H1 --> S1[Specialist A]
        R --> H2[Routing / Handoff Context]
        H2 --> S2[Specialist B]
        S1 --> F[Final Synthesis]
        S2 --> F
    end

Monolithic 的主要成本集中在：

  • shared context 很大
  • session history 很長
  • prompt compaction 壓力很高

Multi-agent 的主要成本集中在：

  • call 次數增加
  • fresh spawn 時 handoff summary 增加
  • 未共享快取時 prefixes 被拆開重複出現
  • 還要再做一次合併

兩個極簡例子

例子 1：單領域請求，Multi-Agent 可能更合理

假設你的系統有四種 specialist：

  • billing
  • support
  • compliance
  • analytics

如果 monolithic agent 每次都要帶著這四組 domain instructions 與 tools， 那即使使用者只是問一個 billing 問題，你仍然可能在每輪都送：

  • 12k shared domain context
  • 2k system / policy
  • 1k current task

大約就是：

15k input tokens

如果你用 router + billing specialist：

  • 1k routing prompt
  • 4k billing specialist context
  • 1k task / handoff

大約可能是：

6k input tokens

這種情況下，multi-agent 很合理。

因為它真正節省的不是智慧，而是：

不相關領域根本不用進 context

而這件事不只可能省 token， 更重要的是能直接降低 context pollution。

例子 2：高共享長任務，Monolithic 反而可能更合理

換另一種情境。

你在做 coding agent，任務需要反覆使用：

  • 同一份 repo summary
  • 同一組 coding rules
  • 同一批 tools
  • 同一段逐步累積的 session history

如果拆成：

  • planner
  • coder
  • reviewer

很可能三個 agent 都需要讀到大量相同的 repo context。

這時候你付出的可能是：

  • planner 讀一次
  • coder 再讀一次
  • reviewer 又讀一次
  • 中間還要再加 handoff summary

即使每個 local context 比 monolithic 小， 總和也可能比單一 agent 更大。

這種情況下，monolithic agent 透過更好的 caching 與 compaction，反而可能更合理，也可能比較省。

重點不是哪個比較「聰明」，而是：

共享上下文太重，而且每個 worker 都從 fresh context 開始時，拆 agent 很可能只是把 shared context 重複付費。

反過來說，如果 execution mode 允許子 agent 繼承父 agent 的上下文或 prompt cache， 那 multi-agent 的重複成本可以明顯下降。

什麼情況 Multi-Agent 真的比較值得拆

Multi-agent 比較值得拆，通常先不是因為它比較便宜， 而是因為它能顯著降低 context pollution。

如果下面這些條件成立，成本才比較有機會一起變好。

1. domain context 彼此高度分離

如果不同 specialist 需要看的知識域差很多， 那 context isolation 的價值就很高。

2. 不同角色的 tools / guardrails / objective 會互相干擾

如果 planner、executor、reviewer 放在同一個 prompt 裡容易互相拉扯， 那拆開的價值就很高。

3. 一次任務只會啟用少數 specialists

如果大部分 request 其實只會走 1 到 2 個 specialist， 那 routing 開銷就有機會被節省下來的 context 抵消。

4. 任務可以 parallel fan-out

如果幾個子任務彼此獨立，parallel fan-out / gather 不只可能降低 latency， 有時也能讓每個 agent 的 local context 保持更小。

5. handoff 可以被壓成小而穩定的 structured payload

如果你能把 handoff 控制成：

  • 任務 ID
  • 幾個關鍵欄位
  • 少量摘要

那 coordination overhead 會低很多。

6. routing 準確率夠高

如果 router 經常錯，multi-agent 的理論優勢很容易被誤路由吃掉。

7. execution mode 支援 shared cache 或 inherited context

如果 worker 可以直接重用共同背景，而不是每次從零開始， multi-agent 的成本表現會好很多。

這裡真正關鍵的不是「有沒有多 agent」， 而是：

  • shared context 是不是每次都要重新送
  • handoff 是不是可以縮成很小的 payload
  • stable prefix 能不能跨 agent 被重用

這也是為什麼同樣都叫 subagent，實際成本可能差很多。

一個很具體的例子：Claude Code 的兩種 subagent 成本模型

Claude Code 的公開文件就把這件事切得很清楚：

  • named subagent 會從新的 context 開始，使用自己的 system prompt，與主對話分開快取
  • forked subagent 則繼承父對話的上下文、system prompt 與 tools，第一個 request 可以重用 parent 的 prompt cache

所以同樣都是把工作丟給子 agent，成本模型其實完全不同。

前者比較接近本文前面講的 fresh specialist spawn； 後者比較像在共享背景上另外開一條工作支線。

這個例子要說明的不是某個產品比較好， 而是 execution mode 本身就會改變 context cost shape。

什麼情況 Monolithic 反而更合理

Monolithic agent 比較合理，通常表示你更需要 continuity 與共享背景， 而不是強隔離。

1. 大多數步驟都共享同一份背景

如果任務每一步都高度依賴同一組 context， 那 shared context 本來就是系統的核心。

2. 任務偏短，但互動連續

這種情況下，session continuity 本身很有價值。 拆 agent 反而會多出很多不必要的 handoff。

3. tool surface 雖大，但實際使用模式高度重疊

如果不同「專家」其實老是在調用相同的一批 tools， 那多 agent 可能只是表面上的模組化。

4. handoff 內容很難壓縮

有些任務的上下文很難被摘要成短 payload。

例如：

  • 長程式碼修改
  • 複雜架構決策
  • 長 research trail

這種情況下，handoff 往往會變成新的 token sink。

真正應該量什麼

如果你已經確認這個任務的一階需求， 再來比較 monolithic 與 multi-agent， 最不該看的就是單次 prompt 長短。

更有價值的觀測指標通常是：

  • model calls per user task
  • total input tokens per task
  • duplicated stable prefix ratio
  • handoff summary tokens per task
  • per-agent / cross-agent cache hit rate
  • specialist activation rate
  • final synthesis tokens
  • parallel fan-out 的 latency / token trade-off

LangChain 的 multi-agent 文件其實直接把幾種 pattern 拿來比較：

  • model calls
  • tokens processed
  • repeat request 的行為差異

這很值得注意。

因為它提醒我們：

agent topology 不是抽象架構風格，而是會直接改變成本曲線的 runtime design。

這件事其實會回頭影響 Context Architecture

如果把這篇和 context caching / compaction / memory 這些概念放在一起看， 會更清楚。

Monolithic agent 更依賴 compaction

因為它的主要風險是：

  • shared history 太長
  • prompt blob 越來越大
  • 需要在同一條 session 裡持續壓縮

Multi-agent 更依賴 handoff discipline

因為它的主要風險是：

  • 同一件事被重複摘要
  • fresh spawn 時同一份 prefix 被不同 agent 各帶一遍
  • state transfer 不乾淨，導致重複上下文

如果 execution mode 可以直接繼承上下文，handoff 壓力會下降； 但相對地，context isolation 也會變弱。

兩者都需要 cache discipline

不管你是一個 agent 還是很多 agent， 只要 stable prefix 不穩，成本都會上升。

Memory architecture 會放大或縮小差異

如果每個 specialist 都各自 retrieval 同一批知識， multi-agent 的 token duplication 會變得更嚴重。

如果 memory 可以被共享、索引一致、按需載入， multi-agent 才比較有機會把 context 切乾淨。

一個更實用的對照表

Topology主要價值主要成本風險更依賴的紀律

結論

monolithic agent 與 multi-agent 的差異，很容易被理解成「簡單架構 vs 進階架構」。

但我覺得更準確的理解是：

Multi-agent 通常先是在解 context pollution。 Monolithic 通常先是在保留 context continuity。 context cost shape 是這兩種選擇的後果，不是起點。

Monolithic agent 的主要問題是：

一個大腦背了太多共享上下文

Multi-agent 的主要問題是：

很多小腦在反覆協調與轉譯上下文

但這句話也要再補一個條件：

如果每個 worker 都從 fresh context 開始， 這種協調與轉譯成本會特別高。

如果系統允許 inherited context、shared state 或 shared cache， 那 multi-agent 的成本曲線會往另一個方向移動。

如果任務的大部分步驟都共享同一份背景、需要長 session continuity、工具使用模式高度重疊，而且 handoff 很難壓縮， 那 monolithic agent 往往更合理，也更穩定。

如果任務的知識域彼此分離、一次只會啟用少數 specialists、可以 parallel fan-out， 而且 handoff 可以結構化，甚至能設計 shared cache 或 inherited context， 那 multi-agent 通常更值得。

所以真正成熟的判準不是 agent 數量， 也不是單輪 prompt 長短， 而是你的任務形狀，到底更需要 context sharing，還是 context isolation。

從這個角度看，agent topology 就不只是軟體模組化問題， 也不只是 cost architecture。

它其實也是：

context architecture

的一部分。

不是越多 agent 越進階， 而是要讓上下文形狀、成本形狀與任務形狀對齊。

Figma AI Agent Engineering Workflow

Figma-to-Code 之前：用 Design Evidence Pack 接住 AI 與團隊分工

Figma-to-Code 真正難的地方，不是把畫面翻成 JSX，而是判斷畫面裡哪些內容可以直接實作，哪些內容還需要業務、系統和團隊補充。

現在的設計輸入也不只是一份 Figma file。它可能是完整的 Figma frames，也可能是 Figma MCP／Code Connect 提供的 design context、Stitch 產生的 UI exploration、Claude Design 做出的 prototype，或一張 screenshot。

這些輸入的完整度不同。它們都能提供線索，卻不會自動變成 business rule、API contract、資料權限和驗證條件。本文把這些線索整理成一個我稱為 Design Evidence Pack 的工作模型，再接到 SA、SD、前端、後端與 QA 的交付流程。

Coinbase 的 Figma-to-Code 案例提供了另一個重要參考：AI 可以承擔大量重複的 translation work，但前提是團隊要準備 reference implementation、rules document 和 prompt templates，並把生成流程拆成可規劃、可驗證、可 review 的 slices[1]。

flowchart TD
    A[Multiple design inputs] --> B[Design Evidence Pack]
    B --> C[SA: Business Requirements]
    C --> D[SD: Technical Design]
    D --> E[Frontend and Backend contracts]
    E --> F[Implementation and verification]
    G[Reference implementation and rules] --> H[AI translation workflow]
    A --> H
    H --> E

設計輸入不是同一種規格

不同工具提供的資訊密度和可信度不一樣。先分清楚輸入能回答什麼，後面才知道要補哪些 evidence 和決策。

輸入可以提供什麼通常還缺少什麼
Figmaframe、component、variant、token、layout、prototype linkbusiness rule、API semantics、資料設計
Figma MCP／Code Connect[3]design context、變數、元件與 code component mapping、可引用的節點資訊domain decision、完整 production architecture
Stitch[2]UI variant、layout exploration、初步 frontend codeapproved design、domain model、backend contract
Claude Design 或其他 multimodal agentprototype、flow draft、screen exploration、spec draftsource confidence、正式決策、production contract
screenshot／wireframe視覺結構、layout、互動線索元件語意、狀態、資料、權限與 responsive 規則

這張表不是用來選出唯一最好的工具。完整 Figma file 可能適合需要元件、變數和 prototype 關係的工作；MCP／Code Connect 可能適合需要節點引用和 code mapping 的流程；Stitch 或 Claude Design 適合快速探索；screenshot 則適合把一個畫面的視覺層次一次交給 agent。

輸入越接近探索稿，越需要補來源、版本和 approved status。輸入越接近正式設計，也不代表 business semantics 和 technical contract 已經完成。設計輸入的完整度，和 production 規格的完整度，是兩件事。

Coinbase 的 screenshot 選擇：有用，但不是答案

Coinbase 的案例值得參考，因為它沒有把「使用 AI」寫成一句口號，而是說明 agent 實際拿到什麼，以及怎麼從輸入一路產生 code。

他們的 frontend workflow 會把每個 Figma tab 截成 screenshot，再交給 agent。Coinbase 選 screenshot 而不是 API-based design integration，是因為 screenshot 能一次保留頁面的 visual hierarchy 和 component relationship；他們也認為 structured design data 可能把視覺層次攤平，並增加上下文成本[1]。

這是 Coinbase 對自身工作流的取捨，不是「screenshot 比 Figma 完整」的結論。Screenshot 對視覺理解很直接，但它可能沒有 Figma 的 component metadata、variables、prototype semantics，也沒有 Code Connect 的 code component 對應。需要節點引用、變數或設計系統 mapping 時，Figma MCP／Code Connect 可能更合適；Stitch 或 Claude Design 則可能更適合早期探索，但要另外處理來源可信度、approved status 和 production constraints。

所以，screenshot 是一種可行的 agent input，不是完整度最高的 input。它是視覺證據，不是 production specification。

Design Evidence Pack：把線索變成可交接的 evidence

Design Evidence Pack 是本文提出的工作命名，不是 Figma、Coinbase 或業界標準。它也不是另一套設計工具，而是放在設計輸入和正式規格之間的一層整理方式。

它要解決的問題很簡單：不同角色不要各自重新解讀原始設計，也不要讓 agent 把看見的內容、合理推測和尚未決定的事情混在一起。

每筆 evidence 可以先用這個最小格式記錄：

EVID-001
source: Figma node URL, prototype, export, or screenshot
source_type: Figma | MCP | Stitch | Claude Design | screenshot | wireframe
observed: 設計上明確看得到的內容
inferred: 從視覺或互動合理推測的內容
unknown: 從目前輸入無法判斷的事情
confidence: high | medium | low
related_nodes: 相關 frame、component 或 prototype flow

不同輸入留下的資料不必一樣：

  • Figma 可以附 frame、node、component、variant 和 token。
  • Figma MCP／Code Connect 可以附 design context、變數和 code mapping。
  • Stitch／Claude Design 可以附 prototype、prompt、版本和產出來源。
  • screenshot 可以附 viewport、截圖時間和原始畫面來源。

例如，畫面上有一個 Create 按鈕：

observed: 畫面上有 Create button
inferred: 點擊後可能建立一個 resource
unknown: 是否需要二次確認、誰可以操作、失敗後是否可重試

Create 是設計 evidence；它對應哪個 business operation，仍要由後續分析決定。這個區分可以讓 agent 先整理問題，而不是把推測直接寫成需求或技術決策。

Coinbase 如何讓 AI 參與實作

Coinbase 的三個 input 並不神奇，很多團隊原本就有類似的文件和程式碼。值得參考的是，他們把這些資產整理成 agent 可以重複使用的 translation workflow。

Reference implementation：讓 agent 讀懂團隊慣例

Reference implementation 是一個完整、已經符合團隊做法的實際 feature。它讓 agent 看到的不只是單一元件，而是 component、route、data fetching、命名、測試、permission 和註冊方式如何一起運作。

Coinbase 的觀察是，輸出品質會跟 reference implementation 的品質一起變化。只給一個視覺相似、但架構和資料流完全不同的頁面，agent 學到的可能只是表面樣式；真正有用的參考實作，必須能代表團隊希望複製的結構與慣例[1]。

Rules document：把 review 標準前移

Rules document 把原本散落在 code review、文件和資深工程師習慣裡的要求寫清楚，例如：

  • page structure、component pattern、naming 和 data fetching。
  • permission、validation、error handling、audit logging 和 service registration。
  • lint、type check、format、query compilation、tests 與 coverage gates。

它的作用不是替團隊決定 business rule，而是降低 agent 在已知 convention 上的自由發揮。規則寫得越清楚，越多機械性錯誤可以在生成前被限制，review 才能把時間留給需要上下文的判斷。

Prompt templates：把 feature context 組合成任務

Prompt template 把每次都要重新整理的欄位固定下來，例如 product name、route、endpoint list、設計輸入、reference implementation 和 rules。工程師只需要填入這次 feature 的變數，就能以一致格式啟動 agent。

Prompt 不是品質保證。它只是讓輸入可重複組合的入口；如果設計來源不明、reference 不適用，或規則本身沒有定義清楚，prompt 寫得再漂亮也只會讓 agent 更快產出錯的方向。

Plan、scaffold、slice：控制產出和 review 的大小

Coinbase 一開始讓 agent 一次生成完整 frontend page，得到過 85 個檔案、超過 6,300 行新增內容；backend 版本則是 19 個檔案、超過 14,000 行新增內容。程式可以運作，卻大到沒有人能仔細 review[1]。

後來他們使用 orchestrator pattern：

  1. Plan：agent 先讀取設計並產生 component-by-component plan，等待工程師確認。
  2. Scaffold：建立 folder structure、routing、permissions、空 stub 和 validation gates。
  3. Parallel workers：每個 tab 或 upstream service group 各自實作，開出小型 draft PR。

重新執行 frontend generation 後，原本一個 85-file PR 被拆成 7 個較小的 PR，review cycle 和 git history 都更容易管理[1]。這是流程設計的價值，不是單純換一個模型就會得到的結果。

角色分工仍然是 production 邊界

AI 可以把 translation work 做得更快，但設計輸入沒有表達的內容，還是需要有人負責。原本的分工可以保留，只要把它放進 AI workflow 的交接點來看。

角色主要承接內容不應由 AI 自行決定
Design / UXapproved design、states、responsive、component intentdesign intent 與視覺取捨
SAactor、use case、business rule、scope、acceptance intentbusiness meaning 與需求邊界
SDservice boundary、API、data、permission、NFRtechnical contract 與系統限制
Frontendroute、component、client state、visual acceptanceUI implementation 的取捨與可用性
Backendoperation、schema、validation、persistence、querydomain logic、資料一致性與安全邊界
QAverification IDs、test strategy、quality gates覆蓋範圍與 release evidence

Design / UX 先確認畫面、互動狀態與 responsive intent。SA 從 evidence 補出 actor、use case、business rule 和 acceptance intent。SD 再把業務能力轉成 service boundary、API、資料、權限和非功能需求。前端與後端拿到的是可以直接實作的角色視圖，QA 則把前面的意圖和契約轉成 verification evidence。

這裡的責任不是把 AI 排除在流程外，而是讓每個角色知道 agent 可以加速哪一段，以及哪些判斷不能只靠畫面或生成結果決定。

從設計輸入到實作交付

可以把整個流程收斂成五個交接點：

多種設計輸入
        ↓
Design Evidence Pack
        ↓
SA：Business Requirements
        ↓
SD：Technical Design
        ↓
Frontend / Backend implementation contracts
        ↓
Implementation + Verification

固定輸入與版本

先記錄 feature id、設計來源、版本、approved viewport、design system、reference implementation、repo、已知 route 和 upstream API。只有 screenshot 的功能可以先標成 prototype，不要直接標成 ready for implementation。

先產生 evidence，再形成規格

Agent 可以協助整理 screens、components、states、tokens 和 assets，並標記 observed、inferred、unknown。SA 接著決定系統要支援什麼行為；SD 再決定系統要用什麼契約支援這些行為。

先 plan，再切 implementation slices

不要一開始要求 agent 生成整頁。先檢查 component、screen、service 或 upstream group 的 plan，再建立 route、permission、API、migration 和 test skeleton，最後切成可以獨立 review 的 slices。

每個 slice 至少要有 requirement ID、API ID、tests、owner 和 reviewer。這樣 UI action 才能追到 business rule、API、資料效果和 verification：

UI actionRequirementBusiness ruleAPI IDData effectVerification ID
CreateFE-001BR-001API-001insert resourceAC-001

如果一個 UI action 沒有對應的 business rule、API 或 verification，通常代表規格還缺一段。這裡的 ID 是工作模型，不是任何工具的固定格式。

分層驗證與回寫

驗證至少要分成四層：

驗證層主要問題
Business功能是否符合 use case 和 business rule？
Visual／Interaction畫面、狀態與互動是否符合 approved design？
API／Datacontract、schema、query 和 error behavior 是否正確？
Security／Operations權限、audit、效能、監控與 rollback 是否可用？安全檢查可參考 OWASP ASVS[6]。

前端還要檢查 responsive、keyboard、focus、semantic HTML、accessible name 和 visual diff；accessibility checks 可對照 WCAG 2[5]。後端則要檢查 permission、transaction、query plan、audit 和 upstream error behavior。

這也延續另一個實作原則：不要把「程式能跑」當成「功能已完成」，而要把驗收條件和可重現的 verification 一起交付；可參考自動化測試與上線前驗證的整理。

實作過程出現變更時，回寫到正確層次：技術細節更新 Technical Design，API 改變更新 contract，business semantics 改變則回到 Business Requirements 做決策。這些變更也要同步更新 agent 使用的 rules 和 prompt，否則下一次生成會重新帶入舊假設。

這套模型目前能說到哪裡

Coinbase 的公開案例已經展示幾件事：AI 可以加速重複性的 design-to-code translation；好的 reference implementation 會影響輸出品質；一次生成巨大 PR 會讓 review 變成瓶頸；plan、scaffold 和平行 slices 可以讓產出更容易被審查；AI 對 convention-following code 的表現，通常比需要 domain judgment 的部分穩定[1]。

但本文的 Design Evidence Pack 和角色分工，是把這個案例放回一般團隊流程後提出的工作模型。它還沒有證明：不同團隊都能因此降低返工、不同設計輸入都能得到同樣品質，或 observed／inferred／unknown 一定能降低 AI 產生錯誤需求。

比較準確的結論是：不同設計工具提供不同 evidence，先整理來源和未知事項；AI 的產出品質取決於設計輸入、reference implementation、rules 與 prompt 的組合；分工則讓 business meaning、technical contract 和 verification responsibility 都有明確 owner。

Design Evidence Pack 的價值，不在於宣稱哪個工具最好，而在於接住多種設計輸入，讓角色能沿著同一份 evidence 往下做決策。它是否真的能降低返工，還是要靠團隊自己的 pilot 和結果確認。

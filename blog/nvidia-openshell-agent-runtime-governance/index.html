NVIDIA OpenShell 是什麼？Agent Runtime 的 Sandbox、政策與憑證治理

概念整理｜初次查閱：2026-10-24｜更新：2026-10-29｜未經實測 主要來源：NVIDIA OpenShell 官方文件、GitHub、產品頁、GTC Berlin 2026 報導與新聞稿

2026 年 10 月的柏林，黃仁勳在 GTC Berlin 的主題演講、與德國總理 Friedrich Merz 的對談，以及 Yahoo Finance 訪問裡，數次把 OpenShell 拉到 agent 故事的中心。[17]

他在 GTC 前的 Build-A-Claw 開發者活動裡，把 OpenShell 講成一個 containment system、另一種 operating system；受訪時提到，據報導今年夏天有前沿實驗室的 agent 逃出隔離、入侵 Hugging Face 等網站，並說如果當時有 OpenShell，結果會不同。[18] [19] 他與 Merz 對談時也說，安全不是喊話，是 technology and engineering。[20]

把場景拉回一般開發者：你給 coding agent 一個 container，它確實在裡面跑。但它要裝套件、要 push code、要打內部 API，這些動作各自帶著不同的風險。Container 只回答「它在哪裡跑」，沒有回答「哪個執行檔、可以連到哪個 host、帶哪一組憑證、誰批准了這次放行」。

這就是 NVIDIA OpenShell 想補的那一層。它是一個開源的 agent runtime，主打讓企業執行「fleets of autonomous AI agents」，在 kernel 隔離的 sandbox 裡跑，並用宣告式 YAML policy 控制檔案、網路與憑證存取。[1] [2]

從文件來看，OpenShell 想把 policy enforcement、credential handling、egress 與 audit 統一放到 agent process 外面管理。代價是平台複雜度、Linux 核心相依性，以及一套需要人維護的 policy 語言。這篇先整理它的概念與代價，把它當成一個 agent runtime 治理的解決方案方向來看。

定位：不是 agent framework，也不是單純的 sandbox

先從產品定位來看。NVIDIA 在產品頁說得很清楚：它不是另一個 agent framework，它坐在 Claude Code、Codex、OpenCode、OpenClaw 或自訂 agent stack 下面。[14] 官方產品頁也列出 GitHub Copilot CLI、Hermes、LangChain Deep Agents 等支援路徑。[14]

它也不是「把 process 關進 container」而已。NVIDIA 的區分是：sandbox 是為單一有界任務隔離 process；OpenShell 則是在 agent 的整個生命週期裡治理它的動作，包含 gateway 協調、sandbox supervision、policy-enforced egress、provider credential 處理、inference 存取與 log。[14]

專案採 Apache-2.0 授權。本文查閱時，最新穩定版是 2026 年 10 月 27 日發布的 v0.1.6；以下功能與限制以 v0.1.6 文件為主。[1] [2]

OpenShell 跟主流 agent sandbox 差在哪？

「主流 agent sandbox」其實不是同一種東西。比較常見的有三類：

  • 本機隔離型：Docker、devcontainer、bubblewrap，或 Claude Code、Codex 內建的 sandbox。啟動快、摩擦低，隔離邊界通常是 process 或 container。
  • 遠端／microVM 型：E2B、Daytona、Kubernetes Agent Sandbox，或 gVisor／Kata 這類 runtime。重點在遠端執行、快照、調度與規模。
  • Agent 內建的 permission／approval 層：Claude Code 的 allow／ask／deny、Codex 的 approval。它們管的是「這個 tool call 要不要執行」，不是「這個 process 可以連到哪個 host、帶哪組憑證」。

OpenShell 不是這三類的替代品。它比較像在這三類之上再加一層控制面，把 policy 決策放到 sandbox 外面；但它自己也會透過 compute driver 建立 sandbox，不是只在既有 sandbox 外面加一層 proxy。差異可以從幾個面向看：

面向主流 agent sandboxOpenShell
決策位置多在 sandbox 內，或 runtime／harness 內在 sandbox 外的 supervisor；sandbox 只攔截與回報
權限粒度process、container、workspace、host／domainbinary + host + port + method + path + MCP tool
網路常是 allow-all、domain allowlist 或簡單 egress proxydefault-deny；TCP／DNS 經 supervisor，支援 L7 檢查
憑證常以環境變數注入 sandboxplaceholder + endpoint binding；必要時動態換 token
治理log、approval、policy hookpolicy prover、policy advisor、OCSF／OTel
可移植性常綁定特定 runtime 或產品policy 與 Docker／Podman／K8s／MicroVM 解耦
營運成本對使用者較輕，適合單人、單任務較重，需要 gateway、DB、IAM

OpenShell 這一側的細節，分別在後面的架構、policy、憑證與治理章節。[3] [5] [7] [9] [10] [12] 這裡的比較是架構層次的整理；各產品實際行為仍以各自文件為準。

多數 sandbox 回答「agent 在哪裡跑、能不能連網」；OpenShell 進一步追問「哪個執行檔、在什麼授權下、帶哪組憑證、對哪個 endpoint 做了什麼」。想先了解 sandbox 的基本概念，可參考Agent Sandbox 的介紹。

這裡有兩個要分清楚的地方。

第一，OpenShell 的隔離強度取決於你選的 runtime。它可以用 Docker、Podman、Kubernetes 或 MicroVM；如果你選 MicroVM，隔離就來自那層 VM。OpenShell 自己加的是 policy、credential 與 audit，不是新的 hypervisor。如果你的威脅模型是 malicious code 逃逸，microVM 或 gVisor 可能更直接；如果你的問題是 agent 亂連網、亂用憑證，OpenShell 補的是那一層。

OpenShell 的價值主要出現在多 agent、多憑證、多環境的情境。若只需要乾淨的執行環境，Docker、devcontainer 或遠端 sandbox 可能更輕。導入成本主要來自 gateway、資料庫、policy 維護與 IAM 整合。

如果要快速選：單人、本機、少量憑證，先用 Docker 或 devcontainer；需要遠端執行與快照，選 remote sandbox；需要 per-binary 的網路政策、憑證代理與 audit，才考慮 OpenShell。

這也是為什麼它和 Claude Code 的 permission 系統不是同一層：Claude Code 在 harness 裡決定 tool call 要不要執行；OpenShell 在 process 外面決定這個 binary 能不能連到某個 endpoint。兩者可以一起用，但解決的是不同問題。

架構：信任邊界畫在 supervisor 與 sandbox 之間

先看 agent、sandbox、container／VM 與 OpenShell 的關係：agent 在 sandbox 的隔離邊界內執行，container 或 VM 負責實作這個邊界。OpenShell 透過 compute driver 建立環境，並把負責網路政策判斷與憑證注入的 supervisor 放在邊界外。[3]

圖：NVIDIA OpenShell 官方架構總覽，依 v0.1.5 文件整理；原圖於 2026-10-27 下載，未修改。來源：〈Architecture〉；原圖標示 Apache-2.0，版權與來源記錄見圖片說明。[3]

讀這張圖時，可以先看左邊的 Gateway、右邊的 Supervisor，再看右側綠色虛線框裡的 agent。綠色虛線框代表整個 sandbox 隔離環境；框內標成「Sandbox」的方塊，則是 OpenShell 用來管理 agent 程序、攔截與轉送網路操作的 runtime 程序。這兩種用法指的範圍不同。[3]

Container 與 VM 是建立 workload 邊界的不同選項，圖中沒有要求兩者一定要疊在一起。真實的 provider 憑證由信任側管理，agent 取得的是 placeholder；請求通過政策與 endpoint 綁定檢查後，supervisor 才代換憑證並對外連線。[3] [7]

OpenShell 把系統拆成幾個角色。[3]

元件位置負責什麼
Gateway控制面管理 sandbox 生命週期、身分驗證、policy 與 provider 派送、連線協調
Compute driver基礎設施層在 Docker、Podman、Kubernetes 或 MicroVM 上建立 sandbox、啟動 supervisor 與 workload、架起網路圍籬
Supervisor信任側檢查每個請求是否符合 policy、解析 DNS、開啟核准的連線、注入憑證
Sandbox與 agent 同側託管 agent process、辨識發出請求的執行檔、攔截 TCP 與 DNS，轉給 supervisor

關鍵在於：supervisor 在 sandbox 邊界外，sandbox 與不被信任的 agent 同側。sandbox 只回報「agent 想做什麼」，不自己做 policy 決定。[3]

目前 Linux backend 的做法是：workload 使用單一非 root 身分、沒有 Linux capabilities；Landlock 限制檔案存取；seccomp user notification 把網路操作攔下來；sandbox 從 /proc 的受信任觀察辨識呼叫的執行檔。[3]

一個網路請求的流程大概是這樣：[3]

  1. agent 開啟 TCP 連線或發出 DNS 查詢。
  2. sandbox 辨識發出請求的程式。
  3. 請求經由 OpenShell Sandbox Protocol 送到 supervisor。
  4. supervisor 對照 policy，必要時加上憑證。
  5. 若允許，supervisor 才開真正的連線並轉送流量。

也就是說，sandbox 對外唯一的 egress 路徑就是 supervisor。外層網路圍籬會擋掉其他所有連線，agent 不能直接碰到服務、gateway、DNS 或另一個私有位址。[3]

這個設計有一個很實際的營運特性：如果 supervisor 斷線，sandbox 會凍結 agent，只有同一個 supervisor process 能重連並恢復。新的 supervisor 就算有合法憑證，也不能接管正在跑的 sandbox。[3] 這是 fail closed 的選擇，代價是 supervisor 的可用性會直接影響 agent 的工作。

runtime 的選擇不影響 policy 行為。Docker 用獨立的 supervisor container 加 Unix socket；Kubernetes 用獨立 pod 加 mutual TLS；VM 用 host process 加 vsock。runtime 只負責建立邊界與證明邊界存在，不決定請求是否放行。[3] 這個切法讓同一份 policy 在不同環境有一致的語意，對平台團隊來說是好事。

OpenShell 也留了幾個 extension point：gateway interceptor 管控制面 API 的治理，supervisor middleware 在 policy 通過後、憑證注入前檢查或改寫 HTTP 與 WebSocket 流量，driver 接 compute 與 secret store，isolation backend 接 sandbox runtime。[13] 這對企業整合很重要，因為 policy 不可能涵蓋所有組織特有的規則；但 middleware 也意味著 traffic 會多經過一層服務，latency 與可用性要一起算。

Policy 才是產品核心

OpenShell 的 policy 是一份 YAML，分成幾個區塊：filesystem_policy、landlock、process、network_policies、network_middlewares。[5]

其中 filesystem、Landlock 與 process 設定在 sandbox 啟動時固定；network rules 與 middleware 可以在執行中熱更新。[5] 這個區分很合理：檔案與身分邊界不該在 agent 跑一半時被改掉，但網路放行可以隨著任務進展調整。

這套設計讓 policy 可以 per-sandbox 調整：每個 sandbox 有自己的 policy，global policy 則是管理者另外套用的覆寫。[5]

預設是 deny。任何沒有被 network_policies 允許的 outbound 連線都會被擋。[6] 每條 rule 列出允許的 endpoints 與可以連線的 binaries，兩者是 many-to-many 關係。[6]

network_policies:
  github_readonly:
    endpoints:
      - host: api.github.com
        port: 443
        protocol: rest
        enforcement: enforce
        access: read-only
    binaries:
      - path: /usr/bin/gh

實際寫 policy 時，有三個地方很容易踩到。

第一，binary 比對用的是執行檔的 real path，不是你在命令列打的指令。pip 是 Python script，所以真正連 PyPI 的是 Python interpreter；rule 要列 interpreter 的路徑。[6] OpenShell 也會在第一次連線時記錄執行檔 hash，之後如果同一個路徑的檔案變了，連線會被拒絕。[6]

第二，protocol 決定要不要做 L7 檢查。rest 可以看 HTTP method、path、query；graphql 看 operation type、name 與 top-level fields；mcp 看 MCP method 與 tool name；tcp 只看 host、port 與 binary，不做 request 檢查。[6] 對 agent 來說，這個差異很重要：只擋 host 不等於擋住 DELETE；只允許 tools/call 也不等於只允許某個 tool，還要再指定 tool 名稱。

第三，overlapping rules 不是有序防火牆。多條 rule 同時 match 時，每一條都會加上它允許的存取；但 deny rule 優先於任何 allow，不管順序。[6] 所以 review policy 時不能只看第一條 match 的 rule。

還有一個文件自己特別提醒的點：access: read-only 是 HTTP method preset，允許 GET、HEAD、OPTIONS，但不保證上游的 GET 沒有副作用。[6] 這個提醒很實在，policy 只能管到請求形狀，管不到服務語意。

Provider 也會貢獻 policy。當你 attach 一個 provider，它的 profile 會把 _provider_* 的 network rule 加進 effective policy。[7] 好處是 GitHub provider 可以自己帶著「允許 api.github.com」的規則，使用者不用在每個 sandbox 複製同一段 policy。壞處是 effective policy 不再等於你手寫的那份，排查時要看 openshell policy get <sandbox> --full。[8]

Gateway 管理員還可以套用 global policy。Global policy 是「取代」每個 sandbox 自己的 policy，不是往上加一層限制；它也會抑制 provider 貢獻的規則。[5] 這是中央治理的強力工具，但語意要先講清楚，不然團隊會以為自己的 policy 還有效。

憑證不進 sandbox，這件事比 sandbox 更難

Agent 的憑證是主要風險之一：它拿到哪一組憑證，又把憑證帶到哪裡。

OpenShell 的做法是：provider profile 描述 credential、endpoint、binary 與 refresh 行為；provider instance 儲存某一組具體憑證；sandbox 裡看到的是 opaque placeholder，真正的值只會在 profile 授權的 endpoint 被替換。[7]

靜態憑證的綁定不是只看 host，還會看 port 與 canonical request path。如果請求帶了某個 provider 的 placeholder，卻送到未被授權的 endpoint，OpenShell 會回 HTTP 403 credential_endpoint_mismatch。[7] 也就是說，network policy 授權「可以連到哪裡」，credential binding 授權「這個憑證可以用在哪裡」，兩者是分開的。

這個分離很重要。很多 sandbox 方案做到「agent 看不到 host 上的 ~/.ssh」，但 agent 還是可能從環境變數拿到一組 token，然後把它送到任何被允許的 host。OpenShell 把「憑證的存在」與「憑證的使用地點」拆開，讓 prompt injection 能偷到的東西變少。

Minimum privilege 的重點，是 runtime 依任務只提供必要的工具與憑證。

動態憑證更進一步。Provider profile 可以宣告 token_grant，由 supervisor 在請求時向 token endpoint 換取短效 access token，再注入 header；支援 client_credentials 與 token_exchange，並使用 sandbox 的 SPIFFE JWT-SVID 作為 client assertion。[7] AWS 的 SigV4 也可以在 proxy 側簽章，sandbox 不需要持有真正的 access key。[7]

Inference 也走同一套。Workload 直接呼叫 provider 的 native endpoint，OpenShell 只負責 policy 與 credential substitution；provider attachment 不會幫你選 model，也不會改寫 model 名稱或 request body。憑證注入與 middleware 是另一層。[8]

產品頁仍以 inference router 描述 OpenShell，但 v0.1.6 文件已說明 workspace-global managed inference route 與 openshell inference 指令已移除，改由 provider profile 綁定憑證、端點與可呼叫的 binary，再讓 workload 呼叫 provider 的原生 endpoint。[8] [14] 舊版的統一 virtual endpoint 不再是 v0.1.6 的做法；評估時要按實際部署版本讀文件。

憑證設計也有它的邊界。已經在跑的 process 不會因為新 attach provider 就長出新的環境變數，要開新 process 才會拿到 placeholder。[8] Profile 的 binaries 路徑也綁定 image layout；路徑不對，憑證不會注入，traffic 也會被 deny。[7] 自訂 base URL 也不能直接沿用 openai 或 anthropic 的範例 profile，因為那些 profile 把憑證綁在公開 vendor endpoint；換 host 要自己匯出、改 endpoint、重新 import。[8]

讓 agent 自己申請權限，但把核准權留在人手上

這是我覺得 OpenShell 最值得看的一段。

Agent 被 policy 擋住時，通常只能停下來等人改 policy。OpenShell 的 policy advisor 讓 agent 在 sandbox 裡提出它需要的 network rule，再由人核准。[10] 這也把「每次 launch 的權限都不同」變成一個可協商的流程：agent 提出需求，人決定要不要給，prover 在中間做風險檢查。

流程是：agent 的請求被 deny，回應會說明被擋了什麼、怎麼申請；agent 讀 sandbox 裡的 guide，透過 http://policy.local 讀目前 policy、看最近的 denial、送出 proposal；OpenShell 用 policy prover 做 risk check，連同 proposal 放進 pending 清單；人用 openshell rule approve 或 reject 決定；核准後 rule 熱載入，agent 重試。[10]

Policy advisor 預設關閉。[10] 無論 advisor 有沒有開，OpenShell 都會從被擋的連線自己草擬 proposal；這些 draft 走同一套檢查與審核。[10]

這裡有兩種檢查，回答的問題不同：[9]

  • Boundary check：candidate policy 是否超出你定義的 boundary policy。用 openshell-prover CLI 跑，主要給 agent 或 CI 用。
  • Proposal risk check：proposed rule 是否比目前 policy 多出風險，例如新的 credentialed reach、新的 HTTP method、cloud metadata 位址。Policy advisor 每次收到 proposal 都會跑。

Prover 用 SMT solver，檢查的是 policy model 裡有建模的特徵：filesystem、process identity、Landlock、network L4、REST。[9] 如果 policy 用了 GraphQL、MCP、WebSocket、JSON-RPC，prover 會回 unsupported，不會假裝檢查過。[9] 但 within_boundary 只代表「在你依賴的範圍內沒有超出 boundary」，不代表 policy 安全，也不代表 runtime 一定照著執行。

自動核准模式也要看清楚。開啟 proposal_approval_mode=auto 後，沒有 risk finding、也沒有被標記的 proposal 會直接通過；但「連到一個新的 public host」本身不算 risk，只要那裡沒有 provider credential。[10] 文件自己提醒，這代表 sandbox 裡的 binary 可以在沒有人看的情況下取得新的 public host 存取。[10] 要開這個模式，最好先想清楚你的 threat model。

觀測、營運與成本

OpenShell 產生 OpenTelemetry traces、Prometheus metrics 與 OCSF JSON events；sandbox log 可以用 CLI 或 TUI 看，OCSF 可以送到 SIEM。[12] 對合規或事故調查來說，這些記錄比 agent 自己的說法可靠：policy 是版控的 YAML，allow/deny 有記錄，官方也強調 credential 值不會出現在 OCSF 事件與 refresh log。[2] [7]

Sandbox 生命週期也做得完整：create、connect、exec、upload/download、port forward、service expose、stop/start、delete，還有 --no-keep 的 ephemeral 模式。[4] 這些看起來是基本功能，但對「agent 跑一整天」的情境來說，stop/start 與 service forwarding 會直接影響可操作性。

成本不在 CLI，而在平台。Gateway 需要資料庫（Helm 預設 SQLite，HA 用 PostgreSQL）、OIDC、TLS 憑證、Kubernetes 或 Docker/Podman 環境；多副本還要處理 peer routing 與憑證輪替。[11] 這不是一個「裝個 CLI 就結束」的工具，比較像一個小型控制面。

我會怎麼看它的 trade-off

適合的場景：平台團隊要讓多個 coding agent 或長時間執行的 agent 共用一套授權模型；企業需要把「哪個 agent 用了哪組憑證、連了哪個 API」變成可審計的 policy；agent 要碰 GitHub、雲端 API、內部服務，但不想把長期憑證放進 sandbox。

不一定適合的場景：只想要一個乾淨的執行環境，Docker 或 devcontainer 可能就夠；單人開發、追求最低摩擦的本機 workflow；Windows 原生環境（目前只有 WSL 2 + Docker Desktop 是 experimental）；或是 kernel 不支援 Landlock ABI 3 的舊 Linux。[11]

  • 執行環境有明確門檻。 Linux backend 需要 Landlock ABI 3（Linux 6.2+）、nested seccomp user notification、process_vm_readv 或 /proc/<pid>/mem、SO_BINDTODEVICE 等能力，不是每個發行版或 container runtime 都能直接提供。[11]
  • Policy 與驗證需要專業維護。 作者要處理 binary path、interpreter、real path、hash pinning、L7 protocol 與重疊規則；寫錯時，可能等到 agent 被拒絕才發現。[6] Prover 目前不支援 GraphQL、MCP、WebSocket、JSON-RPC 等 boundary check，遇到會回報 unsupported。[9]
  • 既有防護可能重複處理同一流量。 防火牆、egress proxy、DNS 控制、IAM／Secrets、EDR 與稽核平台，可能已負責部分網路授權、憑證管理或事件記錄。若每層都再代理、檢查和記錄同一請求，就會增加延遲、政策同步與故障排查成本。[3] [13]
  • 版本仍在快速演進。 穩定版大致每週發布，API 與行為仍會改變；文件列出的後續項目包括 credential placement、binary-scoped injection，以及在 sandbox 啟動時自動執行 policy prover。[7]
  • 廠商整合增加，實際採用仍待觀察。 2026-10-21 NVIDIA 在 GTC Berlin 宣布 OpenShell Reference Architecture，整合 Vera Rubin、Vera CPU 與 BlueField-4 上的 Sentry，並宣稱 Sentry 可在毫秒級隔離越界 agent。[15] 這是 NVIDIA 的產品說法；OpenShell 軟體本身不需要 Vera CPU。[14] Red Hat 也表示正把 OpenShell 接進 Red Hat AI Factory。[16] 廠商投入不等於一般開發者與企業已廣泛採用。

因此，企業評估時要先把控制責任攤開來看：現有哪一層負責網路邊界、哪一層識別 agent 與執行程式、憑證由誰保管、政策由誰維護、紀錄要送到哪裡。如果現有 proxy 已能辨識 agent 身分並執行相同粒度的授權，OpenShell 帶來的新增價值可能有限；如果現有控制只看來源網段或共用服務帳號，它補上的則是 agent 層的權限與憑證邊界。

還要把流量路徑算進去。OpenShell 會讓 sandbox 的 egress 經過 supervisor；若後面還要串企業 proxy 或 TLS inspection，延遲與故障點都會增加。Gateway 可以在 Kubernetes 上部署多個副本，但需要外部 PostgreSQL；這處理的是 Gateway 控制面的可用性，sandbox 的 supervisor 仍是各自流量路徑上的關鍵元件。[21] 導入前應以實際 agent 工作負載量測延遲、吞吐量與故障恢復時間，再判斷新增的 agent 專屬控管是否值得這筆成本。

概念先整理，採用情況還要觀察

這篇依照官方文件與公開資料整理，沒有實際操作。平台需求與支援範圍列在官方 Support Matrix；macOS 僅支援 Apple Silicon。[11]

讀完文件，我仍覺得這套設計不太直覺。OpenShell 橫跨 Gateway、Supervisor 與 sandbox 內的 runtime 程序，底下又有 container／VM 的選擇；network policy 與 provider 的憑證綁定也各有一套規則。要理解一次請求為什麼被拒絕，得先分清楚這幾層各自負責什麼。

它提出的問題值得記下來：agent 的權限、憑證與對外連線，需要有 agent 自己無法繞過的控制。但要讓團隊接受這套方案，還得有人負責寫 policy、處理被擋住的請求，以及維護 Gateway。這些工作會不會比各自管理 agent 更省事，光看架構圖還無法回答。

目前引用的資料以官方文件與廠商公告為主，還不足以判斷實際採用情況。OpenShell 提供 agent runtime 治理的一種做法；學習與維護成本是否划算，仍要看更多實際導入經驗。

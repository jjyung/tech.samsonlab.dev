企業架構實務（九）：企業轉型 Roadmap 規劃指南，如何從目標架構走到可執行的過渡階段與行動計畫

Roadmap 要交代決策順序

完成 gap 識別與行動優先排序後，常見的下一步是畫一張 roadmap：第一季做平台、第二季做資料、第三季做系統遷移。

如果 roadmap 只列時程與專案名稱，還有幾個問題沒有答案：

  • 每一階段要改變什麼能力或行為，為什麼按這個順序推進？
  • 中間要維持哪些過渡狀態，哪些依賴與決策必須先處理？
  • 用什麼證據決定進入下一階段，假設不成立時如何調整或回復？

好的轉型路徑交代從 current state 到 target state 的決策順序與學習節點，日期則依證據和條件逐步排定。

這個觀點可對照 TOGAF 對 Architecture Roadmap、work packages、Transition Architectures 與移轉計畫的區分：Roadmap 說明如何逐步實現 target，移轉計畫則進一步安排交付工作。[1] [2]

三個狀態要同時存在

Baseline：我們現在在哪裡

Baseline 除了現有系統清單，還要記錄：

  • 目前能力與流程如何運作
  • 哪些資料、系統與介面有明確 owner
  • 已知的風險、限制、人工 workaround 與技術債
  • 哪些假設仍然沒有證據
  • 當前的交付與營運指標

沒有 baseline，轉型很容易變成用新架構批評舊架構，卻無法說明真正改善了什麼。

Target：希望抵達哪裡

Target state 要描述可觀察的能力與結果：

  • 使用者或業務流程會有什麼不同？
  • 資料責任、系統邊界與整合契約會如何改變？
  • 哪些品質屬性與治理要求必須成立？
  • 用什麼指標確認結果達成？

Target state 描述後續每個 initiative 都要對照的可觀察能力與結果。

Transition architecture：中間怎麼活著走過去

企業通常無法一次從舊狀態跳到目標狀態。過渡架構描述某個階段「暫時允許什麼共存」，以及這個暫時狀態如何被控制：

  • 舊系統與新服務如何並存？
  • 哪一邊可以寫入，哪一邊只讀？
  • 資料如何同步，短暫不一致是否可接受？
  • 新舊介面如何相容與觀測？
  • 何時停止使用舊路徑？誰負責決定？

過渡架構有明確期限、責任與退場條件，說明中間狀態如何運作。若沒有管理過渡方案，雙寫、雙維護與人工對帳就容易延續下去。

過渡架構中的元件可以分成四種狀態，方便在每個階段說清楚哪些能力正在發生什麼事：

TOGAF 將 Transition Architecture 描述為 baseline 與 target 之間具架構意義的中間狀態，並建議依能力增量、商業價值、風險和組織承接能力安排階段。這支持了「過渡狀態要能運作並產生可辨識成果」的設計原則。[1]

狀態要回答的問題例子
新增本階段要建立哪些原本不存在的能力？新增企業 API 平台、IAM 或集中監控
保留哪些既有能力仍符合需求，需要繼續支撐業務？保留既有核心交易系統
過渡哪些新舊能力需要並存，如何逐步移轉？API 與既有點對點介接並行
替換哪些舊能力何時可以完全淘汰？新平台成熟後下線舊 API Gateway

這四種狀態讓 roadmap 同時呈現「何時做」與「每個階段的架構如何運作」。

Roadmap 若只呈現幾個未來架構快照，仍可能看不出實際由哪些專案與遷移工作完成轉變。Buckl 等人提出的 EA Roadmap 視圖，便把架構狀態、專案工作與支援移轉放在時間脈絡中呈現。[3]

Roadmap 如何接上交付計畫

名稱主要用途典型內容
Roadmap表達方向、階段與順序能力、結果、依賴、里程碑與決策閘門
Project plan管理一個交付單位範圍、工作、時程、資源、風險與驗收
Backlog管理可執行工作user story、技術工作、缺陷與優先級
Action plan指定下一步責任行動、owner、期限、所需決策與檢查方式

Roadmap 描述目標架構如何透過工作套件與過渡架構逐步實現；Implementation and Migration Plan 再安排專案、資源、時程與相依性。Project plan 管理單一交付單位，backlog 管理可執行工作。若把各層內容塞進同一份文件，後續很難確認該由誰更新哪一部分。[1] [2]

要把規劃產物接到可持續執行的 EA 演進流程，Ernst 與 Schneider 也提出涵蓋相關任務與角色的方法模式，並連結專案組合和應用生命週期管理。[4]

投資組合不等於實施路徑

方案被選進投資組合後，仍要依能力和依賴安排啟動順序。可以先分成三個能力階段：

階段主要目的常見能力
建立基礎能力建立後續方案共同需要的穩定環境標準化流程、基礎工具、資料品質、DevSecOps、組織能力
建立共通平台能力讓多個系統可以重複使用企業服務API 平台、IAM、監控、共用服務與治理
建立企業能力將成熟的基礎與平台能力轉成業務價值MDM、資料分析、AI、CRM 與生態圈整合

排定路徑時，除了方案重要性，也要檢查三種依賴：

  • 能力依賴：後續能力需要前置能力，例如資料品質改善先於 MDM。
  • 治理依賴：平台或服務需要先有標準、角色、權責與管理機制，例如 API 治理先於 API 平台擴大採用。
  • 營運依賴：新能力需要監控、支援、回復與持續營運能力，例如集中監控先於大量導入共用服務。

如果沒有分析依賴，所有方案同時啟動容易造成資源衝突、等待、返工與重複建置。TOGAF Phase E 也要求整合差距、方案與依賴，並將企業的變革承接能力納入過渡架構規劃；這些條件會影響路徑與階段安排。[1]

補充模型：單一能力的演進

若要描述單一能力本身如何演進，可以用四階段簡化模型：

能力建立（做法尚未一致）→ 能力標準化（多個團隊遵循共通流程）→ 能力平台化（以共用平台與治理支援多個系統）→ 能力企業化（持續優化並支援業務創新）。

本文整理的四階段模型只用來描述單一能力的發展，不能拿來排序轉型方案或當作通用 EA 成熟度標準。若要評估 EA 管理計畫，可參考 GAO 的七階段 Enterprise Architecture Management Maturity Framework；兩者評估對象不同。[7]

例如 API 能力可以從各系統各自開發，逐步走向規格標準化、共用平台，再支援外部整合等企業場景。這能補充說明單一能力目前在哪裡、下一步要到哪裡。

一個案例：沿用好味餐飲的情境故事

以下沿用〈情境故事：好味餐飲的數位轉型起點〉中的虛構案例。好味有 42 家門市、3 個品牌，OneFood 已從 POS 後端成長為多通路共用的交易核心。會員活動尖峰時，訂單、付款、庫存批次與營運報表同時使用正式資料庫，曾造成多個通路逾時、交易狀態不明與大量人工清查。

Roadmap 要支援好味兩年內擴展至 80 家門市、推出新品牌與開放加盟，同時改善交易可靠度及交付速度。目標包含：未受影響的門市與通路仍可接單、結果不明的交易在 30 分鐘內查明、人工核對降至每月 50 筆以下、營運資料在 5 分鐘內可查，以及一般活動與規則變更在 10 個工作天內完成驗證並上線。規劃也要保留既有 POS 設備至少三年，容許外部服務商各自變更，並確保加盟店只能查看獲授權的門市資料。

Phase 0：建立可決策的 baseline

先沿用缺口分析中的 G-01 至 G-05，確認基線、責任人與驗收方式：

  • G-01 資訊與治理：盤點訂單、付款、庫存與廚房狀態的定義、來源、更新責任及人工對帳原因；為業務目標指定資料來源與負責人，並固定指標的量測口徑、觀察期間與安全門檻。
  • G-02 整合：抽樣串起通路請求、付款、OneFood 訂單與廚房單，確認重送、重複及結果不明的交易如何識別。
  • G-03 品質與技術：量測一般午餐尖峰及七倍活動流量，檢視庫存批次、報表與訂單交易對共用資料庫的影響，補足端到端交易觀測；同時確認日常接單、付款與外送整合、POS 設備年限及加盟資料權限等限制。
  • G-04 流程與交付：確認六週發布週期、四至五個工作天人工回歸及整版回復的原因，找出可先縮小驗證的變更範圍。
  • G-05 人員與能力：確認跨模組事故處理所需角色、現有技能、責任歸屬與備援；目前 14 名相關人員中只有 2 人能獨立追查，且尚無指定備援。

決策閘門：基線資料、目標衡量方式、關鍵責任人與不得中斷的營運限制是否已確認？是否已有足夠證據比較候選方案並選定一個範圍有限、可回復的驗證項目？

Phase 1：驗證一段端到端交易路徑

  • 依基線選定一個具代表性的品牌、通路或門市範圍，維持既有 POS 與外部服務商運作。
  • 依候選方案選擇測試環境、影子觀測或限量正式流量；開始前先定義訂單與付款的寫入責任、停止條件及回復負責人，避免新舊路徑重複建立交易。
  • 驗證同一次結帳能否跨通路請求、付款、訂單與廚房單追查，並明確處理重送、重複及付款結果不明等例外。
  • 在這段路徑補上交易階段、錯誤分類與負載觀測，並測試活動流量與批次、報表同時執行時的影響。
  • 演練故障時的門市處理、交易查明、回復與升級流程，記錄實際耗時和人工介入點。

決策閘門：在 Phase 0 定義的範圍與量測口徑下，抽樣交易能否沿路徑查明，結果不明的交易能否在 30 分鐘內確認？測試期間是否避免重複付款與訂單？負載或依賴故障時，未受影響的門市與通路能否繼續接單？若證據不足或觸及停止條件，先縮小範圍、補足量測或回復既有路徑。

Phase 2：逐步擴展並建立交付與營運能力

  • 將已驗證的交易識別、狀態定義與例外處理逐步擴展到其他通路、品牌及門市。
  • 為共用資料、交易流程及整合介面指定 owner；建立相容性、權限、變更通知與問題升級方式。
  • 將常見活動與規則變更納入小範圍回歸、自動化驗證及可回復的發布流程。
  • 依權限矩陣驗證加盟店只能讀取自己的門市資料，顧客與付款資料仍由總部控管。
  • 持續追蹤人工核對量、營運資料時效、交易查明時間、發布週期與第一線支援負擔。

決策閘門：擴大前是否已通過 Phase 0 列明的安全與營運門檻？人工核對量、營運資料時效、一般規則變更週期等指標是否持續朝目標改善？負責團隊與備援是否能自行處理例外、回復與資料修正？

Phase 3：擴大到成長計畫並退場已無必要的舊路徑

  • 依前階段成效逐步支援新門市、新品牌及加盟店，檢視新門市設定與驗證是否由 15 個工作天縮短至 5 個工作天、新品牌是否能在 8 週內推出第一版、新通路是否能在 4 週內推出第一版。
  • 只有在替代流程已被實際使用、資料責任與回復方式明確後，才遷移或停止直接存取正式資料庫的報表、批次及其他舊路徑。
  • 保留既有 POS 設備的使用期限，並為付款、發票、ERP 與外送等不同步變更的服務商維持明確的整合及例外處理方式。
  • 以事故紀錄、發布紀錄、查明時間、對帳量及展店週期等指標檢視投資成果；尚未達標的項目回到 roadmap 重新排序。

這條路徑先取得足以選擇方案的證據，再驗證有限範圍的端到端交易，最後依可觀察的營運成果擴展或退場。案例沒有預設要採用特定產品、平台或拆分方式；是否進入下一階段，取決於前一階段的證據與決策閘門。

本例的 Phase 0 至 Phase 3 表示推動順序與決策閘門。完成 baseline 後，再依可用資源、預算，以及董事會每半年檢視投資的節奏，排定時間窗口，確認路徑能支援兩年成長目標。

設計路徑：先排結果與依賴

1. 先確認要改變的結果

每個階段先寫 outcome，再列出要支援它的 initiative。例如：

  • 重要客戶資料有明確來源與修正責任
  • 查詢流量不再直接壓在核心交易系統
  • 新通路可以透過穩定契約接入
  • 事故可以被定位、回復與事後追蹤

結果清楚後，才開始決定需要哪些 initiative。這可以降低「為了完成專案而完成專案」的風險。

2. 找出前置依賴

依賴除了系統上線順序，還包括：

  • 資料定義與 ownership 決策
  • 權限、稽核與安全邊界
  • 平台、環境、團隊技能與維運責任
  • 外部供應商、法遵或合約期限
  • 量測與觀測能力

initiative 缺少關鍵前提時，可以拆成「先取得證據」與「再進行改造」兩個階段，先處理阻礙再安排後續工作。

3. 優先安排可降低不確定性的工作

有些工作不會立刻帶來完整功能，卻能讓後續決策更可靠，例如：

  • 建立資料欄位與來源盤點
  • 補上 API／事件的 trace 與錯誤分類
  • 對核心流程建立 contract test 或回歸基準
  • 做一個小範圍的容量、延遲或資料同步實驗
  • 驗證新舊路徑的切換與回復方式

這類工作用低成本換取後續方案的 learning value，並應有明確問題、時間盒與決策輸出。Carnegie Mellon 軟體工程研究所提出的 Architecture Options Workshop，會從已識別的系統風險出發，整理設計選項，再形成實施 Roadmap，可作為前置探索工作的參考。[6]

4. 為每個階段設定決策閘門

決策閘門要確認是否有足夠證據，支撐下一階段成本較高、較難回復的變更：

  • 目標行為是否真的被使用者需要？
  • 資料責任與品質是否已經清楚？
  • 效能、可用性、安全與營運負擔是否可接受？
  • 團隊是否具備長期維護能力，包含處理例外、回復服務與持續改善？
  • 過渡架構的退場條件與責任是否已經成立？

證據不足時，可以延後、縮小範圍、補驗證，或停止方案；不必為了守住原時程繼續投入。

六項考量歸成三組

設計 roadmap 的順序時，可以把六項考量歸成三組問題：

  • 價值與時機：是否支援策略、法規、重大痛點或近期價值？
  • 可行性：前置能力是否到位？關鍵人力、技能與預算是否足夠，是否需要分階段投入？
  • 風險與承接：是否需要先用 Pilot 驗證？使用單位、流程與制度是否準備好接受改變？

「高價值」代表值得討論，實際啟動仍要看前置能力與承接條件。Roadmap 的結構與規劃流程也要配合議題範圍、參與者和決策用途，才能支援策略溝通與後續行動。[5]

從路徑拆成 action plan，並持續治理

要把能力實作出來，可以拆成四層：

能力
→ 工作項目
→ 主要活動
→ 里程碑

此外，每一項行動計畫至少要寫清楚五件事：目標、要建立的能力、負責單位、時程，以及成功衡量指標。里程碑只是代表某個交付物或階段完成；成功指標則要證明能力真的被使用並產生價值，兩者不能混用。TOGAF 的移轉計畫也將工作分解、相依性、資源、成本、風險、里程碑和時程納入規劃，說明 Roadmap 需要連回可交付與可追蹤的工作。[2]

Action plan 可以先用一個小表格開始：

行動對應結果與前置條件主要 owner／相對時程完成證據衡量指標／檢視點
定義交易狀態、資料來源與責任G-01；交易樣本、現行狀態文件與對帳紀錄資料 owner（營運、財務協作）；Phase 0 gate 前狀態與欄位字典、來源及 owner 對照、未決事項責任人人工核對降至每月 50 筆以下，營運資料 5 分鐘內可查；Phase 0 定義口徑，Phase 2 檢視

每項行動都要能回到一個 gap 或 outcome。若說不出它要解決的問題，就要重新確認是否需要納入轉型工作。

表中的 Phase 是相對時程示意；正式執行時，需指定實際負責人與起訖時間，並將階段檢視排入半年投資決策節奏。

階段完成後更新 roadmap

每個階段完成後都要更新 Roadmap，至少回寫：

  • 哪些 target behavior 已驗證，哪些 gap 已關閉或只是被轉移？
  • 哪些假設、依賴、風險或優先級需要修正？
  • 過渡架構增加了哪些維運或資料成本，下一階段是否仍值得投入？

EA 要根據專案交付結果、incident 與使用者回饋持續更新。記錄架構狀態、變更工作與遷移時點，可以保留 Roadmap 的演進脈絡，支援後續檢視。[3]

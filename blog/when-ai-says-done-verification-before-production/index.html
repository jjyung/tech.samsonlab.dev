當 AI 說「做完了」，我們到底該相信什麼？

當 AI 說「做完了」，我們到底該相信什麼？

現在很多人在談 AI 開發風險時，還是會把問題收斂成一句「AI 產出品質不穩」。

現在的問題，很多時候已經不是 AI 會不會寫，而是它寫得越來越快之後，我們到底要靠什麼相信它真的做完了，而且做對了。

如果只是 demo，很多事情都可以先過。畫面能跑、流程能動、測試有幾個綠燈，通常就足以讓人往下一步走。

但只要開始碰真實專案，問題就會完全變樣：

  • 這個結果是不是只是看起來合理？
  • 它是不是漏掉了最重要的邊界情境？
  • 它說已完成，到底是指文字上完成，還是有證據支持的完成？
  • 如果換一個人、換一個 agent、換一條 pipeline，還能不能得到同樣結論？

我後來越來越覺得，AI 時代真正需要被工程化的，不是生成，而是驗證。

我原本以為，review 壓力只是暫時變重

一開始我比較直覺的想法其實很簡單。

AI 把程式寫快了，團隊的 review 壓力當然會變大一點，但本質上應該還是同一套工程問題。多補一些測試、多做一些 code review、多跑幾輪 CI，大概就能接住。

後來我發現，事情沒有那麼單純。

因為 AI 帶來的改變，不只是產出速度提升，而是把整個 bottleneck 往後推了。以前最花時間的是寫出來，現在越來越花時間的是判斷這個東西到底能不能信。

尤其在任務規模一變大之後，風險常常不是它直接亂寫一通，而是它會持續產生一個看起來很合理的進度敘事。每一步都像是有在推進，每一輪回報也都像是有在收斂，但真正被驗證過的東西，可能比你以為的少很多。

這種情況麻煩的地方在於，它不像傳統 bug 那麼容易被看見。你不是看到明顯錯誤才出事，而是先相信了那個「應該差不多好了」的感覺，最後把不確定性一路帶進 production。

問題不是 AI 會不會出錯，而是我們怎麼定義「完成」

我覺得這裡真正要改的是完成定義。

如果今天一個 agent 跟你說「這個功能已完成」，那到底代表什麼？

如果完成只是：

  • 它自己說完成了
  • PR 看起來很完整
  • 測試全部綠燈
  • demo 跑起來沒問題

那這個完成其實還很脆弱。

因為 PR 綠燈不代表測到真正重要的情境，demo 能跑也不代表系統邊界已經被覆蓋。很多 production 問題不是因為實作完全錯，而是因為那個最該被驗證的情境，根本沒進到驗證流程裡。

所以我現在比較傾向把「完成」定義成下面三件事：

  • 有客觀證據支持，不是只有模型回報
  • 能被另一個人或另一套流程獨立驗證
  • 能重跑、能重現，而不是一次性的對話結果

這三件事看起來很普通，但其實會直接改變團隊怎麼設計 AI workflow。

因為一旦你接受這個定義，就很難再把驗收停留在「它說沒問題」這個層次。

真正要驗的，通常不是現在這段程式，而是它背後的假設

這也是我最近最有感的一個轉變。

以前講驗證，我第一個想到的是 correctness。功能有沒有照需求跑、測試有沒有過、輸入輸出有沒有對。

但 AI 產物最麻煩的地方，常常不是表面上跑不跑得動，而是它會偷偷把一堆沒講清楚的假設補進去。

例如：

  • 它假設某個商業規則永遠成立
  • 它假設某個例外流程不重要
  • 它假設使用者行為會很單純
  • 它假設未來維護的人看得懂這段設計

這些東西如果沒被挑出來，系統一開始可能真的能跑。但之後只要需求一變、資料一髒、流量一上來，問題就會開始冒出來。

所以好的驗證，不只是檢查「有沒有寫對」，而是主動去問：

  • 哪些測試其實還沒寫？
  • 這個實作偷偷依賴了哪些前提？
  • 哪些情境是現在流程根本沒覆蓋到的？
  • 半年後別人接手時，最難理解的地方在哪？

這些問題比單純檢查 syntax 或 style 更重要。因為它們處理的是風險外溢，不只是程式碼表面品質。

這裡我也想到台灣長期推廣敏捷與測試的 David Ko 柯仁傑，最近幾場公開分享其實都在講很類似的事。 [4] [5]

他的切入點不是反對 GenAI 介入測試，而是反對把 GenAI 想成一台自動出題機。用他的說法，AI 產出的測試個案，真正的問題從來不是「生不生得出來」，而是：

  • 真的能照表操課去執行嗎？
  • 涵蓋率真的夠嗎？
  • 不懂測試的人，真的能只靠 prompt 就把它做好嗎？

他在 WebConf Taiwan 2025 的議程介紹裡，也把自己的經驗與判斷說得很清楚：功能與系統測試若要在 GenAI 時代真正落地，背後還是要靠 Specification by Example、Exploratory Testing 和 test case design techniques 這些基本功，AI 只是把這些能力放大，不會憑空替代它們。[5]

我覺得這個觀點很重要。因為它把「測試案例生成」和「驗證能力」切開了。前者是產出速度，後者才是產品信心。很多團隊會把這兩件事混在一起，以為 test cases 變多，就等於 verification 變強，但其實兩者差很遠。

如果把視角拉到更國際的工程社群，Martin Fowler 最近幾篇談 AI coding agent 的文章，其實也在往同一個方向收斂。[6] [7] [8] [9] [10]

他沒有把焦點放在「模型會不會越來越強」這件事，而是把焦點放在 harness、review loops 和 sensors。換句話說，真正能提升信任的，不是多喊幾次「請仔細檢查」，而是你有沒有把規格、檢查點、持續監測與回饋訊號包成一套外部結構，讓 agent 的輸出不是只能靠人類事後猜。

這個角度我很認同。因為它提醒我們，verification 不該只是最後補救，而應該是整個 workflow 的一部分。

這也是為什麼我越來越在意 Verification Engineering

如果只是把 AI 當輔助寫碼工具，也許還能把驗證視為開發後段的一個步驟。

但如果團隊真的開始把 agent 放進需求分析、規格轉換、程式生成、測試生成、維運排查這整條流程裡，那驗證就不該只是最後一道 QA 關卡，而應該是一層獨立的工程能力。

我自己會把它先粗分成幾個面向：

  • 完成條件要先被定義清楚，而不是事後解釋
  • 驗證要能獨立執行，不能完全依賴同一個生成脈絡
  • 測試不能只驗 happy path，還要刻意找邊界、例外與對抗情境
  • 決策、工具操作與驗證結果要留下紀錄，方便追溯與重跑
  • 高風險動作要有 gate，不是產物一生成就直接往下游送

這件事一開始看起來像流程變重，但我後來覺得它比較像是把原本藏著的風險顯性化。

因為沒有 verification 的高速交付，不是真的快，只是把錯誤更快送進系統裡。

Fowler 提到的幾個概念，其實很適合拿來幫這件事命名。[6] [7] [8]

像是 generate-review loop，本質上就是把「先做，再複核」變成顯式流程；maintainability sensors 則是在說，你不能只在 PR 那一刻看結果，而要讓 coverage、dependency、drift、runtime feedback 這些訊號持續存在，變成 agent 與團隊共同面對的約束。

我會把這理解成：verification 不只是 QA 的工作，而是整個系統用來累積信心的感測層。

如果把這件事再往敏捷和團隊協作的脈絡看，其實也說得通。

敏捷從來不是比較快把東西做出來而已，而是比較早拿到回饋、比較快修正方向。放到 AI 開發也是一樣。真正符合敏捷精神的，不會是「agent 很快做完，所以我們快點 merge」，而是「我們有沒有更早把假設攤開、更早把風險驗掉、更早知道這個結果到底值不值得信」。

這也是為什麼像 David Ko 這類長期做敏捷測試的人，會一直把重點放回需求共識、例子、探索與設計技法。因為這些東西本質上都不是在追求更多產出，而是在追求更早、更準確的回饋。換句話說，它們其實就是 verification 的前置工程。

不一定每件事都要逐行 review，但一定要有能擋錯的結構

這裡還有一個很現實的問題。

當 AI 產出越來越多之後，團隊不可能永遠靠人逐行把每一段都看完。這不只是效率問題，也是注意力問題。人類 review 本來就有極限，AI 只是在把那個極限更早推到你面前。

所以我不會把答案理解成「那就更努力人工 review」。比較合理的方向反而是：把人力從逐行檢查，移到設計更好的驗證環境。

Kent Beck 對這件事的描述也很到位。[11] [12] [13] 他最近在談 code review 時就很直接承認，傳統 review 在 AI 加速之前其實就已經有點撐不住了，只是 AI 把這個問題徹底放大。PR 放著等、reviewer 沒時間、最後變成 LGTM 式橡皮圖章，這些都不是新問題，只是以前大家還勉強能忍。[11]

一旦生成速度被拉高，這套做法就更不可能是主力。因為不是 reviewer 不努力，而是回饋迴路本身已經跟不上。

他另外一個我很喜歡的觀點，是把多個 AI assistant 之間的不一致，當成一種 verification 訊號。也就是說，不要急著追求單一模型給出唯一答案，反而可以把不同工具的分歧拿來暴露假設、比較設計、逼自己做更有意識的判斷。[12] [13]

例如：

  • 哪些測試一定要先存在？
  • 哪些規格必須先文件化？
  • 哪些改動一定要經過獨立 gate？
  • 哪些結果要能被 replay？
  • 哪些權限不能直接交給 agent？

換句話說，重點不是人到底有沒有看過每一行，而是錯的東西能不能被結構性地擋下來。

這和傳統工程其實也一致。好的流程本來就不是靠英雄式檢查撐住，而是靠一套讓錯誤不容易溜過去的設計。

Trade-off 也很現實

當然，verification 不是一句話喊完就沒有代價。

你把驗證做重，通常就會一起帶來幾個成本：

  • 前期要花更多時間定義完成條件
  • 測試與驗證腳本本身也需要維護
  • 團隊流程會變得比較慢，至少在短期內是這樣
  • 有些小型任務如果也套同樣強度，反而會過度設計

所以這不是叫大家把所有 AI 任務都升級成高監管流程。

比較務實的做法應該是分級。

低風險、可逆的小任務，可以給比較輕的驗證；高風險、跨系統、不可逆、會直接影響使用者或資料的任務，就必須有更重的 verification gate。

這裡真正困難的地方，不是工具怎麼選，而是團隊願不願意先把風險邊界講清楚。

結尾

我現在會把這件事理解成一個很實際的轉向。

AI 讓生成變便宜了，所以工程價值自然會往更稀缺的地方移動。那個地方不是 prompt 寫得多漂亮，也不是 agent loop 跑得多花，而是我們能不能建立一套讓結果可被信任的交付方式。

所以如果今天要問一個比較值得問的問題，我覺得不是「AI 能不能幫我做產品」，而是：

  • 它說做完了，我憑什麼相信？
  • 如果它漏了最重要的情境，誰會先知道？
  • 如果明天換一個人接手，這個結果還能不能被驗證回來？

這些問題如果沒有被制度化回答，AI 帶來的效率，多半只是把風險更快擴散。

但如果 verification 能夠被當成一層正式能力來設計，AI 才比較有機會真的從 demo 走進 production。

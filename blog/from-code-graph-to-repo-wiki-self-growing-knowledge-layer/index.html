Code Graph 到 Repo Wiki：用 LangChain OpenWiki 讓文件跟著程式碼更新

假設團隊把付款失敗後的重試次數從三次改成一次。程式和測試都改了，架構文件卻還寫著三次。下次請 coding agent 修改付款流程時，它可能先讀到這份文件，而且不一定知道哪一句已經過時。

我之前寫過怎麼用 Graphify 追程式碼。放到這個例子裡，graph 可以幫忙找出哪個服務負責重試、有哪些呼叫端。但如果想知道當初為什麼只留一次重試，就得去翻 PR 討論或架構決策紀錄，前提是團隊有把理由留下來。

把查過的程式行為和決策理由寫進 Repo Wiki，下次接手就能沿著來源查。程式碼再改時，得回頭核對 Wiki 裡受影響的說法。Karpathy 的 LLM Wiki 提供了一種整理方式，LangChain 的 OpenWiki 則讓我們看到，這個想法放進程式碼庫後可以怎麼運作。

LLM Wiki：把查過的知識留下來，下次不用重查

Andrej Karpathy 是 OpenAI 的創始成員之一，也曾負責 Tesla 的 AI 團隊。2026 年 4 月 4 日（UTC），他在 X 分享 LLM Wiki 的做法，並把這套模式整理成一份 GitHub Gist。 [1]

他談的原本是個人知識管理。用檢索增強生成（RAG）查資料時，模型會找出相關段落，再為這次的問題整理答案。Karpathy 的做法是保留原始資料，另外讓 LLM 維護一批互相連結的 Markdown 頁面。加進一份新來源時，LLM 不只寫一份摘要，也回頭更新相關頁面，標出哪些說法互相矛盾。下次再問，就能從前面整理過的內容接著查，必要時再回去看原始資料。

這個點子後來也被拿來做程式碼庫的文件。LangChain 在 OpenWiki 的發布文裡，把 LLM Wiki 和 DeepWiki、AutoWiki 一起列為靈感來源。 [2] 整理這篇文章時，我也用了類似做法。原始來源留在 raw/，整理後的內容放進 wiki/，有新資料就更新相關頁面。

OpenWiki 怎麼讓 Wiki 跟著程式碼更新？

LangChain 在 2026 年 7 月 1 日發布 OpenWiki，讓團隊可以用 CLI 為程式碼庫建立 Wiki。openwiki --init 會把 Markdown 頁面寫進 openwiki/，並在 AGENTS.md 放一個入口，讓 coding agent 需要了解架構或找流程時，再去讀相關頁面。

程式碼改了，可以跑 openwiki --update。OpenWiki 會參考上次更新以來的 Git 變更，找出需要回頭檢查的內容。它也能把「即時請款失敗後只重試一次」這類說法記成一筆 Grounded Claim，連到特定版本的檔案與行號。當相關證據變動時，更新流程就能重新確認這句話還成立、需要改寫，還是該撤回。 [3]

有了 Repo Wiki，還需要 Code Graph 嗎？

以付款重試來說，Code Graph 可以幫我往下追是哪個 service 做重試，也能往上查有哪些呼叫端。但它沒辦法單靠呼叫關係告訴我，當初為什麼從三次改成一次。要回答這個問題，還是得看 PR 討論或架構決策紀錄（ADR）；如果當初沒留下理由，就只能先標成待確認。

我會在 OpenWiki 的更新流程之外，用 Code Graph 補查呼叫關係。程式碼有變動時，可以先用 Git diff 找出改了哪些檔案，再用 graph 往外追可能受影響的呼叫端。Agent 確認程式碼、設定和測試後，才回頭更新 Wiki 裡相關的說法。下次有人問哪個入口會重試，就能先看整理好的答案，也知道該去哪裡核對。

我會先留一頁 Markdown：列出哪些入口會重試、次數由哪個設定控制，再附上程式碼、測試和決策紀錄的連結。

大型舊單體適合用 OpenWiki 嗎？

可以試，但我不會從「替整個 repo 產生 Wiki」開始。程式碼太大，先遇到的是生成時間、模型用量，以及團隊有沒有餘力審查文件。程式碼太亂，問題就不只是成本：同一條業務規則可能散在好幾條路徑，實際走哪一條還得看設定、資料狀態或部署環境。頁面寫得再順，也可能只是把其中一條路徑說得很有把握。

沿用付款重試的例子：舊單體可能同時有即時請款、批次補單和人工重送。即使 OpenWiki 找到某段程式確實只重試一次，也不能因此寫成「所有付款失敗都只重試一次」。Grounded Claims 能幫審查者回到版本化的程式碼證據，但證據存在，不代表涵蓋了其他入口，或證明正式環境使用的是同一組設定。至於當初為什麼這樣做，程式碼沒留下的理由，Wiki 也不該代填。

我會先挑一條常被問、有人能審的流程，例如「即時請款失敗後怎麼處理」。在 openwiki/INSTRUCTIONS.md 說清楚這次要涵蓋哪些入口、設定和測試；用 .openwikiignore 排除明確不相關的生成檔或歷史副本，但不要為了縮小範圍，把流程依賴的共用模組也排掉。這兩個設定的用途不同：前者告訴 agent 文件要寫什麼，後者限制它能讀哪些路徑。做完後，拿幾個團隊真的常問的問題來驗收，再挑一次相關的程式碼變更，看 Wiki 有沒有改對地方、審查花了多少時間。 [3]

如果連這條流程都缺少可核對的設定或測試，團隊也沒有人能確認現況，我會先把產出當成導覽：它可以列出可能的入口、證據和待確認事項，但不適合直接當成 agent 修改核心流程的依據。等小範圍的文件真的有人用、改了也有人看，再決定要不要擴到整個單體。

程式改了，Wiki 跟得上嗎？

我比較在意的是，下次有人要改付款重試時，能不能接著上次查到的結果做，不用再從頭翻一遍 repo。Code graph 可以幫 agent 找到受影響的程式和測試；Wiki 則把哪些入口會重試、次數由哪個設定控制，以及還有哪些地方沒確認，留給下次接手的人。

所以我會拿一次真的改動來驗收。假設這次只調整即時請款的重試次數，我會看 agent 有沒有改到對的段落、附上可以核對的程式碼或測試，又有沒有順手把批次補單寫成同一套規則。如果每次審查還是得把整個付款流程重新查一遍，那 Wiki 雖然寫出來了，團隊並沒有省下多少時間。

Wiki 裡留著這次查到的證據，下次改程式時，就有線索能核對哪些說法要一起改。不確定的地方就留待確認，不用為了把文件補齊，替團隊猜一個答案。

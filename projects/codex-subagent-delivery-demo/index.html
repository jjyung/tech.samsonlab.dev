Codex Subagent Delivery Demo

這個 repository 以 Java Library Console 的借書功能為場景，示範如何把需求、設計、API 契約、程式碼、測試與交接整理成一條可以被 Agent 執行、被團隊審查、也能留下驗證證據的交付流程。

這個案例聚焦在「怎麼交付」，不是「怎麼讓 Agent 一次產出最多程式碼」。目前的 demo/20260908-qa branch 把這條流程推進到完整的前後端實作與 QA rework，成為可以逐階段對照的 instructor reference。

這個案例要回答的問題

AI coding 工具可以快速產生程式，但團隊仍然要回答幾個交付問題：

  • 規格由誰維護，Agent 為什麼要這樣實作？
  • 換一個 Codex session 或另一個 Agent，能不能從既有狀態接手？
  • 前後端如何在同一份 API contract 上平行開發？
  • 程式完成後，要用什麼測試與 API response 證明它符合需求？

這個專案把答案放進 repository 裡：SDD 保存 requirements、acceptance criteria、architecture 與 OpenAPI；Codex Skills 固定每個角色要讀什麼、能改什麼、要驗證什麼；Workflow State 記錄目前階段、交付物、阻塞點與 handoff。

從 spec-ready 到可驗證交付

這個流程的關鍵切點是 spec-ready commit。這個 commit 先凍結規格與交接邊界，不包含 Backend 實作，讓新的 branch 和新的 Codex session 可以從同一個起點接手：

Requirements + AC
  -> SA / Archi / SD artifacts
  -> OpenAPI + generator config
  -> spec-ready commit
  -> Backend branch + new Codex session || Frontend branch
  -> Unit / Integration tests + API response
  -> Integration Gate

Backend 由 BE Skill 讀取凍結的 OpenAPI，產生 Java interface 與 DTO，再在 handwritten 區域完成 Controller、Service、repository adapter、validation 與 error mapping。Frontend 則從相同起點產生 client／model 並平行開發。最後，acceptance criteria 對應到 JUnit、integration test、API 驗證與前端測試，讓「完成」不只是一句 Agent 的宣告。

完成版本包含什麼

demo/20260908-qa 將借書案例擴充成可操作的 Library Mini Admin MVP，包含：

  • Java 21、Spring Boot、H2、Liquibase、JDBC DAO，以及由 OpenAPI Generator 產生的 API boundary。
  • Vue 3 前端、generated TypeScript models、openapi-fetch、搜尋／分頁、借還書操作與 responsive layout。
  • requirements、architecture、OpenAPI、schema、API flow、generated code、unit／integration test 與前端測試。
  • workflow state、delivery summary、Playwright fixture、Page Object、E2E 與 QA report。

兩個 branch 要一起看

這個專案的教學價值來自兩個 branch 的對照，而不是只收錄一個 GitHub 連結：

Branch定位閱讀重點
main學員起始狀態Scenario、AGENTS.md、Codex agent／skill 設定、文件模板與 starter workflow；適合用來從頭走一次完整流程。
demo/20260908-qa完成結果與 instructor reference完整規格、設計、實作、generated code、測試、workflow state、交付摘要與 QA report；適合逐階段比對最後留下的證據。

建議先從 main 建立 spec-ready 的概念，再切到 demo/20260908-qa 查看這個起點如何交給 FE／BE，最後如何經過 QA 驗證與 rework。

QA 如何形成 rework loop

demo/20260908-qa 的 QA 報告記錄了 AC-001～AC-009 全數通過、Chromium 完整 suite 6/6 通過，以及 2 workers 下沒有跨測試資料污染。過程中曾發現同一書目有多個複本時，第二筆歸還可能失敗；後端修正 CK_BOOKS_STATUS_MAPPING 後，兩筆借閱可以逐筆歸還，庫存從 1 / 2 回到 2 / 2，狀態恢復為可借閱。

這正是這個 workflow 的 rework loop：QA 不是最後替流程蓋章，而是把可重現的缺陷證據交回實作角色，修正後再用 targeted test、integration coverage 與完整 E2E 回歸。這一輪的 QA 判定為 Pass with limitations；pixel-diff、axe／contrast audit、loading／submit-disabled 的獨立斷言與完整 server-log correlation 未納入本次核心 scenario gate。
